# Работа с VoyahTune

VoyahTune — Android-приложения и системная интеграция для Voyah Free.
Основная целевая платформа: официальные SE и Sport+ 2025–2026, Android 11.
Поддержку других комплектаций и прошивок подтверждай отдельно.

## Структура проекта

- `RestoreMode/` — интерфейс, настройки, главный экран и голосовой помощник.
- `Native/` — привилегированный сервис, OEM API, CAN и управление приложениями.
- `Updater/` — автономная root-служба обновлений и её отдельный Android-интерфейс.
- `RunYN/` — дополнительное Android-приложение PI для выбора и запуска приложения в навигационной карточке приборной панели.
- `Packaging/pi/` и `Packaging/od/` — раздельные системные перехваты, загрузчики и установочные скрипты; общие проверки находятся в `Packaging/tests/`.
- `Installer/` — GUI на Tauri/Svelte, общий Rust-движок и сборщик payload.
- `Utils/` — вспомогательные инструменты и тестовое окружение.
- `versions.json` — единственный источник текущих версий Installer и VoyahTune/payload.
- `Releases/` — локальные результаты сборки; исходники релиза находятся в `Packaging/`. Исключения: каталоги `Releases/ota/index.json`, `index-beta.json` и `index-v4.json` хранятся в Git.

## Документация и рабочие материалы

- Инструкции, справочники, актуальное описание реализации и историю выпусков храни в `Docs/`.
- Планы, аудиты, разборы и чеклисты храни в корневой `Plans/`.
- `Plans/` игнорируется Git: не добавляй её принудительно и не ставь на её файлы ссылки из публикуемой документации.
- `tmp/` содержит локальные APK, декомпиляции и материалы исследований; их может не быть в другом checkout.
- Существенные подтверждённые сведения для сопровождения переноси из рабочих материалов в документацию.
- В этом файле держи устойчивые правила проекта; результаты отдельных задач оставляй в `Plans/`.
- Личные инструкции для конкретного checkout храни в корневом `AGENTS.override.md`, который исключён через `.gitignore` и не публикуется в Git. Codex загружает его вместо соседнего `AGENTS.md`, поэтому в начале личного файла явно требуй прочитать и соблюдать общий `AGENTS.md`; далее размещай личные дополнения.

## Реализация и совместимость

- Используй названия VoyahTune, Native и RestoreMode и термин «релиз» для их выпуска. Не вводи названия редакций, выбор редакции, runtime-режимы редакций и специальные сценарии миграции. Обновление той же инфраструктуры выполняется поверх либо после удаления. Для смены PI/OD пользователь сначала удаляет VoyahTune, затем сам выбирает и устанавливает другой релиз. Не добавляй автоматические миграции, определение перехода, запреты или предупреждения выбора за пользователя.
- Сборка содержимого релиза всегда явно получает ровно один флаг `--pi` или `--od`. Java-база Native/RestoreMode общая; профиль инфраструктуры записывается в подписанные metadata APK и manifest payload. Ресурсы PI и OD не смешиваются; версия релиза включает `-pi`/`-od`, updater соответствует payload. GUI общий для обоих профилей и выбирает инфраструктуру по проверенному manifest. Обычная Gradle debug-сборка использует OD.
- Каталог общий для PI и OD; версии с разными суффиксами — отдельные записи. GUI показывает оба профиля, OTA фильтрует свой профиль до выбора последней версии и скачивания; старые версии без суффикса считаются OD. Публикация по-прежнему требует отдельного поручения.
- Используй существующие OEM-транспорты и обработчики событий; не дублируй доступ к CAN без необходимости.
- При изменении протокола между RestoreMode и Native проверяй обе стороны.
- Различай наличие поля в OEM API, успешную отправку команды и подтверждённое выполнение автомобилем.
- В выводах по декомпиляции указывай исследованную версию и ограничения; общий SDK не доказывает поддержку функции на конкретной машине.
- Не выдавай фиксированные значения интерфейса за измерения датчиков или тест на эмуляторе за проверку на автомобиле.

## Версии и минимумы совместимости

- Перед изменениями Installer/root-службы и перед подготовкой релиза читай корневой `versions.json`. Поле `installer` — версия установщика; `voyahtune` — единая базовая версия VoyahTune и payload. В файле держи только эти два поля со строками `major.minor.patch`. Суффиксы инфраструктуры и beta добавляй при сборке: например, `4.0.0-od` или `4.0.0-beta-od`.
- При сборке установщика бери версию из `versions.json.installer`; при сборке VoyahTune/APK/payload — из `versions.json.voyahtune`. Значения в Cargo, Tauri, Gradle-параметрах, metadata и manifest являются производными, а не независимыми источниками. До запуска сборки синхронизируй необходимые манифесты, требования и параметры с `versions.json`; расхождения исправляй, не выбирай молча версию из другого файла. Номер, передаваемый существующему сборщику аргументом, также бери из `versions.json`.
- Если меняются код, исполняемые ресурсы или логика сборки Installer либо OD root-службы, автоматически, без отдельного подтверждения, повышай `installer` для следующего релиза. По умолчанию увеличивай patch; minor/major — по явному указанию пользователя. Чистые правки документации, тестов и записей каталога не повышают версию. Повышение выполняй один раз для совокупности изменений очередного релиза, а не после каждой правки, проверки или повторной сборки. Уже выбранные пользователем номера текущего готовящегося релиза сохраняй.
- Перед подготовкой обновления каталога и сборкой нового изменённого payload повышай `voyahtune` в `versions.json` (по умолчанию patch, если пользователь не задал другой номер). Используй один и тот же номер в APK, manifest, имени архива и записи каталога. Повторная сборка ещё не опубликованного релиза без новых изменений не повышает номер; опубликованный изменённый архив всегда получает новую версию.
- Для каждого нового OD-релиза записывай текущее `versions.json.installer` как `requirements.minInstallerVersion` внутри payload и как `minimumInstallerVersion` в каталоге. Capabilities сохраняй согласно реальному контракту payload. Фиксированные минимумы в коде сборщика синхронизируй с файлом версий до сборки; не оставляй прежний минимум после повышения Installer.
- Минимум OTA вычисляй до изменения каталога, сравнивая текущий Installer с `minimumInstallerVersion` последнего опубликованного OD-релиза в выбранном каталоге. Предыдущий релиз определяй по SemVer, а не по порядку записей; PI-записи не используй. Если Installer изменился, ставь `minimumOtaVersion` равным новой базовой версии `versions.json.voyahtune`. Это версия установленного VoyahTune, не номер Installer: например, Installer `1.6.1` и payload `4.0.1-od` означают `minimumInstallerVersion: "1.6.1"`, `minimumOtaVersion: "4.0.1"`.
- Если Installer не изменился, переноси `minimumOtaVersion` предыдущего релиза: обычное обновление приложений не должно требовать USB. Для первого релиза пустого каталога или предыдущей записи без сведений о минимумах используй текущую `voyahtune` как минимум OTA. Передавай вычисленный минимум сборщику через `--minimum-ota-version`, не полагайся на его фиксированное значение по умолчанию. Явно согласованный более строгий минимум сохраняй.
- Повышение версий и подготовка метаданных не разрешают сборку релизов, публикацию, коммит или push без соответствующего поручения. Запись каталога с URL, размером и SHA-256 готовь по реально собранному архиву; в публичный каталог добавляй только после разрешённой публикации. Для OD 4+ используй `Releases/ota/index-v4.json`, не подменяй старые каталоги.

## Когда пересобирать установщик

- При каждом релизе оценивай, меняется ли исполняемый GUI или его встроенные ресурсы. Сам новый номер VoyahTune не является причиной пересборки установщика.
- Новый установщик нужен при изменении интерфейса Tauri/Svelte, Rust-движка, порядка установки/удаления, мягкой очистки, миграций, восстановления после ошибок или проверки запуска приложений.
- Пересобирай установщик при изменении поддерживаемой схемы payload/каталога, операций recipe, capabilities, проверки совместимости, загрузки, распаковки, проверки хешей, кэша или встроенного URL каталога.
- Пересборка нужна при замене встроенного ADB, встроенного recovery/remover, зависимостей исполняемого приложения, а также изменении упаковки, подписи или требований к ОС. Собирай затронутые и согласованные платформы.
- Изменения общих APK, hooks, loader, конфигураций и списка файлов/прав в пределах уже поддерживаемого recipe требуют только нового payload и обновления каталога. Если тот же изменённый ресурс входит во встроенный recovery/remover, обнови и установщик.
- Изменения записей каталога, ссылок на опубликованные релизы, документации, тестов или только сборщика payload не требуют нового GUI, пока не меняют его исполняемый код, встроенные ресурсы или необходимый ему контракт. Изменение классических `.sh/.bat` требует пересборки GUI, если изменился переносимый в движок код команд автомобиля.
- Версию установщика и минимумы совместимости повышай по правилам раздела «Версии и минимумы совместимости», в том числе при совместимых изменениях Installer и при изменениях OD root-службы. Изменение root-службы требует нового Installer с актуальным номером для следующей USB-установки.
- В результате работы указывай, нужна ли пересборка установщика и по какой причине. Команды сборки и порядок публикации — в [инструкции релизного процесса](Docs/releasing.md).

## Основной и beta-каталог релизов

- Для OD 4+ основной каталог — `Releases/ota/index-v4.json`; каждая запись содержит version/url/size/sha256 и `minimumInstallerVersion`/`minimumOtaVersion`. Прежний основной каталог — `Releases/ota/index.json`; отдельный beta-каталог — `Releases/ota/index-beta.json`.
- Добавляй релизы в beta-каталог только по явной просьбе пользователя о добавлении или публикации в beta. Создание ветки, реализация функции, сборка и суффикс версии сами по себе такого разрешения не дают.
- При работе с beta не изменяй основные каталоги. Для скриптов обновления явно передавай нужный `--index`: `Releases/ota/index-beta.json` для beta или `Releases/ota/index-v4.json` для OD 4+. Не полагайся на прежний путь по умолчанию.
- Не копируй записи между каталогами и не продвигай beta в основной без отдельного явного поручения. Выбор каталога не заменяет разрешение на загрузку артефактов или push.

## Порядок работы

- Разбивай работу на завершённые шаги и веди чеклист в `Plans/`.
- После каждого шага отмечай фактически выполненное, сообщай прогресс и делай отдельный коммит с его изменениями.
- Сборки и тесты выполняй по завершении крупного этапа; не повторяй их после каждой промежуточной правки без необходимости.
- Не отмечай проверку на автомобиле или публикацию выполненной по результатам локальной сборки. В чеклисте сохраняй ограничения и оставшиеся действия.
- Никогда не создавай резервные копии APK Native и RestoreMode, в том числе перед обновлением на автомобиле.

## Проверки

Выбирай проверки по затронутому компоненту; изменение документации не требует полной сборки.
Команды ниже выполняются из указанного каталога:

- `Native/` или `RestoreMode/`: `./gradlew testDebugUnitTest` — JVM-тесты.
- В том же Android-проекте: `./gradlew assembleDebug` — проверка сборки единых APK, когда изменение её затрагивает.
- `Installer/`: `cargo test` — тесты основных Rust-компонентов workspace.
- `Installer/desktop/`: `npm run check`; для проверки сборки интерфейса — `npm run build`.
- Из корня: относящиеся к изменению скрипты `Packaging/tests/`; инструкции окружения — в `Docs/releasing.md`.
- Перед завершением проверяй `git diff --check`, состав изменений и локальные ссылки в изменённой документации.
- В результате называй выполненные проверки и ограничения. Установку на машину, испытания и публикацию выполняй в рамках явно согласованной задачи.
