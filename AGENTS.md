# Работа с VoyahTune

VoyahTune — Android-приложения и системная интеграция для Voyah Free.
Основная целевая платформа: официальные SE и Sport+ 2025–2026, Android 11.
Поддержку других комплектаций и прошивок подтверждай отдельно.

## Структура проекта

- `RestoreMode/` — интерфейс, настройки, главный экран и голосовой помощник.
- `Native/` — привилегированный сервис, OEM API, CAN и управление приложениями.
- `Updater/` — автономная root-служба обновлений, отдельный APK интерфейса и общая библиотека IPC/UI.
- `RunYN/` — приложение для выбора и запуска приложения в навигационной карточке приборной панели; включено в единый payload, установка зависит от модели автомобиля.
- `Packaging/new/` — единые системные перехваты, Go-загрузчик, конфигурации и boot-ресурсы. Проверки runtime находятся в `Packaging/new/tests/`, общие установочные проверки — в `Packaging/tests/`. Очистка прежних установок находится в общем recipe и `Packaging/installer/common/`; старых runtime-каталогов нет.
- `Installer/` — GUI на Tauri/Svelte, общий Rust-движок и сборщик payload.
- `build-env/` — Dockerfile окружения Linux-сборки payload; запуск через корневой `build_in_container.sh`.
- `Utils/` — вспомогательные инструменты и тестовое окружение.
- `versions.json` — единственный источник текущих версий Installer и VoyahTune/payload.
- `Releases/` — игнорируемые локальные результаты сборки; исходники релиза находятся в `Packaging/`. Каталог релизов обслуживается сервером.

- Существенные подтверждённые сведения для сопровождения переноси из рабочих материалов в документацию.

## Реализация и совместимость

- Используй названия VoyahTune, Native и RestoreMode и термин «релиз» для их выпуска. Все новые сборки единые: не вводи редакции, выбор инфраструктуры и отдельные номера релизов по типу поставки автомобиля. Особенности OEM обрабатываются адаптерами и условиями по модели.
- Собирай единый USB/OTA payload из `Packaging/new/` без флагов выбора профиля и без инфраструктурного суффикса версии. Java-база Native/RestoreMode общая; APK metadata и root-служба используют только `infrastructure: unified`. Деление PI/OD, выбор профиля и подстановка `od` в APK запрещены. Различия OEM учитывай по модели и доступным API; прежние имена допустимы только для миграции и очистки.
- Новый payload имеет фиксированный формат 5: каталог `common/`, версия и формат в метаданных APK, общий типизированный Rust-план установки. Внешние `manifest.json`, `agents.json` и `runtime-manifest.json` не создаются. Изменение установочного контракта требует обновления Installer и при необходимости root-службы.
- Каталог и версия релиза единые. Новый номер имеет вид `major.minor.patch` или `major.minor.patch-beta`. Установка поверх прежних выполняется общим recipe: замена runtime, очистка известных устаревших файлов и перезагрузка Android. Первое обновление несовместимой root-службы выполняется через USB, последующие совместимые обновления — тем же payload через OTA. RunYN устанавливается по условию модели (`except-h97xy`). Исторические идентификаторы сохраняй только для совместимости, не используй их как инструкции новых сборок. Публикация требует отдельного поручения.
- Используй существующие OEM-транспорты и обработчики событий; не дублируй доступ к CAN без необходимости.
- При удалении инфраструктурных профилей проверяй каждую ветку на OEM-различия: сохраняй необходимые триггеры, порядок команд, fallback и защиту пользовательского выбора через модель или доступный API. Общий SDK-класс не доказывает одинаковое поведение прошивок; у автоматического восстановления должен быть один владелец.
- При изменении протокола между RestoreMode и Native проверяй обе стороны.
- Различай наличие поля в OEM API, успешную отправку команды и подтверждённое выполнение автомобилем.
- В выводах по декомпиляции указывай исследованную версию и ограничения; общий SDK не доказывает поддержку функции на конкретной машине.
- Не выдавай фиксированные значения интерфейса за измерения датчиков или тест на эмуляторе за проверку на автомобиле.

## Версии и минимумы совместимости

- Перед изменениями Installer/root-службы и перед подготовкой релиза читай корневой `versions.json`. Поле `installer` — версия установщика; `voyahtune` — базовая версия stable-релиза VoyahTune и payload. В файле держи только эти два поля со строками `major.minor.patch`. Для beta добавляй суффикс при сборке: например, `4.5.0` или `4.5.0-beta`.
- При сборке установщика бери версию из `versions.json.installer`; при сборке stable VoyahTune/APK/payload — из `versions.json.voyahtune`. Для beta используй явно заданный пользователем номер сборки, а если он не задан — базовую версию из файла; `versions.json.voyahtune` при этом не меняй. Значения в Cargo, Tauri, Gradle-параметрах, metadata являются производными, а не независимыми источниками. До запуска сборки синхронизируй необходимые манифесты, требования и параметры с выбранной версией; расхождения исправляй, не выбирай молча версию из другого файла. Передавай выбранный по этим правилам номер сборщику аргументом и используй его согласованно во всех артефактах.
- Повышай `installer` только при технической необходимости выпустить новый установщик: меняются его исполняемое поведение, встроенные ресурсы, упаковка или поддерживаемый установочный контракт. Само обновление root-службы не требует новой версии Installer, если текущий установщик совместим с форматом payload, операциями recipe и capabilities новой службы; такую службу доставляй в payload через USB существующим совместимым установщиком. Чистые правки документации, тестов, каталогов или сборщика payload без изменений самого установщика не повышают его версию. При необходимом повышении по умолчанию увеличивай patch без отдельного подтверждения; minor/major — по явному указанию пользователя. Повышение выполняй один раз для совокупности изменений очередного релиза, а не после каждой правки, проверки или повторной сборки. Уже выбранные пользователем номера текущего готовящегося релиза сохраняй.
- Меняй `voyahtune` в `versions.json` только при сборке stable-релиза payload (по умолчанию повышай patch, если пользователь не задал другой номер). Beta-сборки, разработка и подготовка каталога это поле не меняют. Используй один и тот же номер сборки в APK, имени архива и записи каталога. Повторная сборка ещё не опубликованного релиза без новых изменений не повышает номер; изменённому опубликованному stable-архиву назначай новую версию сборки.
- При пересборке и обновлении beta сохраняй полную существующую версию: не меняй ни основную часть `major.minor.patch`, ни номер/суффикс beta; не добавляй автоматически `.2`, `.3` и другие номера. При разрешённой публикации перезаписывай архив и сопутствующие метаданные существующей beta по прежним путям, обновляя размер и SHA-256 в той же записи beta-каталога. Например, обновление `4.5.0-beta` остаётся `4.5.0-beta`. Это явное исключение из запрета перезаписи опубликованных релизов; запрет продолжает действовать для stable. Само правило не разрешает публикацию без запроса пользователя.
- Для каждого нового релиза задавай одинаковую минимально необходимую совместимую версию Installer в `minimumInstallerVersion` метаданных APK и `minimumInstallerVersion` в каталоге. Не подставляй автоматически текущую `versions.json.installer`: новый выпуск Installer или совместимое обновление root-службы сами по себе не повышают этот минимум. Повышай его только при технической необходимости на стороне установщика; иначе сохраняй прежнее требование. Capabilities и параметры сборщика должны соответствовать реальному контракту payload.
- Единственная проверка допуска к OTA — `minimumOtaVersion`. Не добавляй в OTA проверки размера/SHA-256 архива, подписи APK, совпадения метаданных/версий или capabilities. Сохраняй обработку фактических ошибок распаковки, записи и запуска, защиту файловых путей и восстановление после прерывания. Проверки компьютерного установщика и аутентификация IPC остаются самостоятельными механизмами.
- `minimumInstallerVersion` ограничивает установку через компьютер, `minimumOtaVersion` — обновление по воздуху. Не выводи один минимум из другого или из факта повышения версии Installer. Минимум OTA определяй по совместимости установленной root-службы с новым релизом. Если для релиза необходима новая служба, доставляемая через USB, ставь `minimumOtaVersion` равным базовой версии VoyahTune, впервые содержащей эту службу, без beta-суффикса. Это версия установленного VoyahTune, не номер Installer.
- Если обновление root-службы через USB для нового релиза не требуется, переноси `minimumOtaVersion` предыдущего опубликованного совместимого единого релиза в выбранном каталоге. Предыдущий релиз определяй по SemVer, а не по порядку записей. Обычное обновление приложений или Installer не должно само по себе требовать USB. Для первого единого релиза с новой службой используй базовую версию собираемого payload как минимум OTA. Передавай вычисленный минимум сборщику через `--minimum-ota-version`, не полагайся на фиксированное значение по умолчанию. Явно согласованный более строгий минимум сохраняй.
- Повышение версий и подготовка метаданных не разрешают сборку релизов, публикацию, коммит или push без соответствующего поручения. Запись каталога с URL, размером и SHA-256 готовь по реально собранному архиву; в публичный каталог добавляй только после разрешённой публикации. Текущий каталог читается через `https://voyahtune.ru/api/v1/releases`; локальные JSON-индексы не ведутся.

## Когда пересобирать установщик

- При каждом релизе оценивай, меняется ли исполняемый GUI или его встроенные ресурсы. Сам новый номер VoyahTune не является причиной пересборки установщика.
- Новый установщик нужен при изменении интерфейса Tauri/Svelte, Rust-движка, порядка установки/удаления, мягкой очистки, миграций, восстановления после ошибок или проверки запуска приложений.
- Пересобирай установщик при изменении поддерживаемой схемы payload/каталога, операций recipe, capabilities, проверки совместимости, загрузки, распаковки, проверки хешей, кэша или встроенного URL каталога.
- Пересборка нужна при замене встроенного ADB, встроенного recovery/remover, зависимостей исполняемого приложения, а также изменении упаковки, подписи или требований к ОС. Собирай затронутые и согласованные платформы.
- Изменения общих APK, hooks, loader, конфигураций и списка файлов/прав в пределах уже поддерживаемого recipe требуют только нового payload и обновления каталога. Если тот же изменённый ресурс входит во встроенный recovery/remover, обнови и установщик.
- Изменения записей каталога, ссылок на опубликованные релизы, документации, тестов или только сборщика payload не требуют нового GUI, пока не меняют его исполняемый код, встроенные ресурсы или необходимый ему контракт. Изменение встроенных shell-команд и helpers требует пересборки GUI.
- Изменение root-службы требует нового payload, но не пересборки или повышения версии Installer, если текущий установщик может установить этот payload. Необходимость USB-обновления службы и необходимость нового установщика оценивай отдельно по правилам раздела «Версии и минимумы совместимости».
- В результате работы указывай, нужна ли пересборка установщика и по какой причине. Команды сборки и порядок публикации — в [инструкции релизного процесса](Docs/releasing.md).

## Каталог релизов

- Installer и единая root-служба по умолчанию читают `https://voyahtune.ru/api/v1/releases`. Адрес архива берётся из `url` выбранной записи; идентификатор backend не вычисляется из версии.
- Локальные JSON-индексы и прежняя инструкция загрузки в S3 удалены как устаревшие. Не восстанавливай их и не используй старые скрипты публикации как действующий процесс выпуска.
- Сборка создаёт ZIP и сопутствующую запись с параметрами архива, но не регистрирует релиз на сервере. Не подменяй отсутствие актуальной процедуры публикации прежними командами.
- Публикация, обновление beta и продвижение beta в основной выпуск выполняются только по явному поручению. Суффикс версии, сборка или создание ветки такого разрешения не дают.

## Порядок работы

- Разбивай работу на завершённые шаги и веди чеклист в `Plans/`.
- После каждого шага отмечай фактически выполненное, сообщай прогресс и делай отдельный коммит с его изменениями.
- Сборки и тесты выполняй по завершении крупного этапа; не повторяй их после каждой промежуточной правки без необходимости.
- Не отмечай проверку на автомобиле или публикацию выполненной по результатам локальной сборки. В чеклисте сохраняй ограничения и оставшиеся действия.
- Никогда не создавай резервные копии APK Native и RestoreMode, в том числе перед обновлением на автомобиле.
- Комментарии в коде пиши только по существу, они должны быть полезны, описывать неочевидные связи и нюансы поведения. Не описывай в комментариях прошлое измененное поведение. Комментарии должны быть на английском языке, короткими и содержательными
- Не пиши на каждую итерацию документацию - собирай важные нюансы и разборы, планы, чеклисты в tmp, в Docs переноси только короткие содержательные с важными деталями вещи.
- Код и именование файлов должны быть человекочитаемыми, самодокументируемым, отражать сематический смысл.
- Оформление кода должно быть с учетом современных практик и принятых норм на код ревью в индустрии. Должны использоваться нормальные названия переменных и классов, без сокращений. Должны быть переносы строк и отстуты чтобы отделять конструкции друг от друга.
- Конкатенации строк предпочитай оставлять в одну строку, если они образуют семантически понятную конструкцию (например, подпись со значением и единицей измерения). Длинные выражения переноси по смысловым границам, сохраняя такие фрагменты целыми; не разбивай каждый операнд `+` на отдельную строку только ради форматирования.
- Если правишь код, который выбивается из правил стилистики - поправь его стиль во всем файле сразу
- Любую работу начинай с формирования чеклиста в md файле в папке Plans, дели работу на эти шаги, по завершении шага отмечай выполнение в чеклисте. Если получаешь новые задачи - вноси их в отдельный список после основного и переход на этот новый список делай с коммитом текущей завершенной работы. Уточнения по текущей работы сразу вноси в текущий чеклист.
- Все работы по DiPlay фиксируй в carplay-diplay.md для дальнейшего обновления и миграции на новую версию из оригинального репозитория. Документ должен включать в себя все технические особенности, которые меняются относительно оригинала.

## Проверки

Тесты должны быть содержательными: вызывать рабочую реализацию и проверять
конкретный результат или наблюдаемый эффект на разных входных данных. Для
проверяемого поведения охватывай обычные, граничные и ошибочные случаи, когда
они применимы. Тест должен обнаруживать нарушение этого поведения, а не просто
подтверждать значения собственных тестовых заготовок.

Не создавай и не сохраняй тесты документации и структуры исходного кода:
проверки фраз README/Docs, наличия или порядка фрагментов исходника, имён
внутренних методов, форматирования, количества вызовов по тексту и аналогичные
проверки через grep, регулярные выражения или разбор AST. Не заменяй поведенческий
тест копией реализации внутри теста или проверкой одних статических объявлений.
Арифметические шаблоны вроде `2 + 2 = 4` и проверки только имени пакета не нужны.

Фиксированные входные данные и ожидаемые результаты допустимы, если между ними
выполняется рабочий код. Проверки текста, который возвращает приложение,
сериализованных сообщений и реально созданных файлов являются проверками
поведения; запрет относится к проверке написания исходников и документации.
Моки подменяют внешние зависимости, но не проверяемую логику. Проверки синтаксиса,
типов и сборки остаются отдельными инструментами и не считаются поведенческими
тестами.

Выбирай проверки по затронутому компоненту; изменение документации не требует полной сборки.
Команды ниже выполняются из указанного каталога:

- `Native/` или `RestoreMode/`: `./gradlew testDebugUnitTest` — JVM-тесты.
- В том же Android-проекте: `./gradlew assembleDebug` — проверка сборки единых APK, когда изменение её затрагивает.
- `Installer/`: `cargo test` — тесты основных Rust-компонентов workspace.
- `Installer/desktop/`: `npm run check`; для проверки сборки интерфейса — `npm run build`.
- Из корня: `sh Packaging/new/check.sh` для runtime; относящиеся к изменению общие проверки — в `Packaging/tests/`. Инструкции окружения — в `Docs/releasing.md`.
- Перед завершением проверяй `git diff --check`, состав изменений и локальные ссылки в изменённой документации.
- В результате называй выполненные проверки и ограничения. Установку на машину, испытания и публикацию выполняй в рамках явно согласованной задачи.
