# BMS Monitor

Android-приложение для головного устройства автомобиля: показывает температуры
батарейного блока и напряжения 90 ячеек. Данные читаются по SSH с T-Box
(`root@172.16.104.20`), где работают утилиты VNS (`/mnt/hirain_app/usr/bin`).

## Сборка и установка

```bash
./gradlew :app:installDebug          # собрать и поставить на устройство (adb)
adb shell monkey -p com.bms.monitor -c android.intent.category.LAUNCHER 1
```

- `compileSdk 35`, `minSdk 24`, Kotlin/JVM 17, ViewBinding.
- SSH — `com.github.mwiede:jsch`.
- Release подписывается debug-ключом.

## Подключение к T-Box

`SshManager` держит одну SSH-сессию и переиспользует её.

| Параметр | Значение |
|---|---|
| Хост | `172.16.104.20:22`, пользователь `root` |
| Пароль | `Settings.Global` → `ssh_tbox_password`; если не задан — `12345`. На машине, где T-Box с паролем `54321`: `adb shell settings put global ssh_tbox_password 54321` |
| Ключ | `Settings.Global` → `ssh_tbox_private_key` — путь к приватному ключу ed25519 (OpenSSH-формат). Если задан — авторизация по ключу вместо пароля: `adb shell settings put global ssh_tbox_private_key /data/local/tmp/id_ed25519`. Отпечаток хоста не проверяется |
| Таймаут подключения | 15 с, keep-alive 15 с |

Все команды выполняются по очереди под одним мьютексом: утилиты VNS нельзя
запускать параллельно. При ошибке сессия сбрасывается, и следующий запрос
подключается заново.

## Экраны

Переключаются нижним меню (`MainActivity`). Экземпляры фрагментов создаются
один раз и переиспользуются, view пересоздаётся при каждом переходе.

### «Температуры» (`TempFragment`)

- Слева — график (`TempGraphView`): X — время (окно 30 мин, «now» справа).
  Левая ось Y — °C (температуры), правая — % (SOC) и `dcl/100`
  (`drivingCurrentLimit`, А / 100). У каждой оси своя
  автошкала (мин. размах 4 °C / 4 %, SOC в пределах 0…100), сетка общая.
- Справа — сетка 2×3 карточек: Max | Min, Outlet | Inlet, предел тягового тока | SOH/SOC/SOE. Цвет подписи совпадает
  с цветом линии на графике, цвет значения — градиент −40 °C (синий) …
  0 °C (зелёный) … +40 °C (красный), см. `ColorUtils.tempColor`.

| Карточка | Сигнал | Цвет серии |
|---|---|---|
| Max | `bms_packTempMax`, под значением «модуль M · датчик S» — `bms_packTempMaxModuleIdx` / `…MaxSensorIdx` (0x574) | оранжевый `#FF7043` |
| Min | `bms_packTempMin`, под значением — `bms_packTempMinModuleIdx` / `…MinSensorIdx` (0x574) | голубой `#4FC3F7` |
| Предел тягового тока | `drivingCurrentLimit` — оценка по `bms_packTempMax`, `≈836 А` | подпись `#E0BC45`, значение `#B89A38`; на графике — серия `dcl/100` (значение / 100, правая ось) цветом подписи |
| Inlet | `bms_tempInletCoolant` | бирюзовый `#4DB6AC` |
| Outlet | `bms_tempOutletCoolant` | фиолетовый `#BA68C8` |
| SOH / SOC / SOE | `bms_SOH`, `bms_SOC`, `bms_SOE` — в одной карточке столбиком, подпись цветом значения | SOC — розовый `#F06292` (правая ось %); SOH и SOE на графике нет |

Значения температур: `12.0 °C`, `N/A` (raw `0x1FF` — недействительно), `—`
(кадр не получен). SOH / SOC / SOE: `95.3 %`, `N/A` (raw `0x3FF`), `—`;
цвет — градиент от красного к зелёному: SOH 70 … 100 %, SOC и SOE 0 … 100 %.
SOC выводится на график по отдельной правой оси, чтобы не ломать шкалу °C.
`bms_packTempAvg` на экран и график не выводится, только в лог (`temp_avg`).

- Снизу — строка из 9 плиток `T1` … `T9`: датчики температуры модулей
  `bms_moduleXTempSensor1..9` (кадр 0x584), подпись и значение в одну строку,
  цвет как у карточек температур. В конце строки, шире — `IsoRes`:
  `bms_isolationResistance` (кадр 0x574), `13141 кОм`, подпись серая `#CACACA`,
  значение белое `#E6E6E6`.

### «Ячейки» (`CellsFragment`)

- Кнопка «Обновить» — чтение занимает ≈6 с, в это время показан прогресс.
- Строка статистики: максимальный и минимальный заряд, дисбаланс
  (max − min; 0 В — зелёный, ≥ 0.040 В — красный).
- Сетка батареек: цвет — относительно min/max текущей пачки (минимальная —
  красная, максимальная — зелёная), т.к. ячейки отличаются тысячными вольта.
- **Резиновая сетка.** При каждом изменении размера (в т.ч. freeform-окно)
  выбирается наименьшее число колонок, при котором все 90 ячеек помещаются
  по высоте (пропорция иконки 48:16.8), но не меньше, чем колонок шириной
  146 dp. Ряды растягиваются на всю высоту, текст масштабируется по размеру
  иконки (не больше 16 sp). Пересчёт идёт через `post {}`, т.к.
  `requestLayout()` внутри прохода layout игнорируется.

## Опрос температур и SOH / SOC / SOE

`MainViewModel.startTemperaturePolling()` — фоновый цикл (при записи лога
вместо `CMD_BMS_CAN` идёт `CMD_BMS_CAN_CELLS` — заодно ячейки, период 10 с,
см. «Запись лога»):

1. `SshManager.CMD_BMS_CAN`:
   ```sh
   timeout -s INT 3 stdbuf -o0 -e0 /mnt/hirain_app/usr/bin/vnsMonitorCan -s:0x514,0x304,0x584,0x574 2>&1 \
     | grep -a -A1 -E "CAN\[(304|514|584|574|111)\]"
   ```
   За 3 с приходит ~30 кадров `0x304 BMS_temperature` (~10/с) и 2 кадра
   `0x514 BMS_metric` (~1/с; при окне 2 с кадр 0x514 иногда не успевал
   прийти). Берётся последний кадр каждого id.
2. `Parsers.parseTempFrame` (0x304) и `Parsers.parseMetric` (0x514) расшифровывают
   кадры.
3. Значения публикуются в LiveData, температуры и SOC добавляются в историю
   (`TempHistory`, скользящее окно 30 мин).
4. Пауза 10 с.

Пока открыт экран «Ячейки», цикл стоит на паузе и не ходит по SSH
(`pause/resumeTemperaturePolling`).

### Раскладка кадра 0x304

Из `/mnt/hirain_app/etc/vns/H97/can-in.xml`. Байты little-endian (Intel),
младший бит сигнала — позиция `startbit − 1`, длина 9 бит,
`°C = raw × 0.5 − 40`.

| Сигнал | startbit | Пример (`68 C8 94 D9 C2 45 0B 00`) |
|---|---|---|
| `bms_packTempMax` | 1 | `0x68` → 12.0 °C |
| `bms_packTempMin` | 10 | `0x64` → 10.0 °C |
| `bms_packTempAvg` | 19 | `0x65` → 10.5 °C |
| `bms_tempInletCoolant` | 28 | `0x5B` → 5.5 °C |
| `bms_tempOutletCoolant` | 37 | `0x5C` → 6.0 °C |

### Раскладка кадра 0x514 (SOH / SOC / SOE)

Тот же `can-in.xml`, та же нумерация битов, 10 бит, `% = raw × 0.1`.

| Сигнал | startbit | Пример (`AA E6 6E E2 3F 64 BE 00`) |
|---|---|---|
| `bms_SOC` | 1 | `0x2AA` → 68.2 % |
| `bms_SOH` | 11 | `0x3B9` → 95.3 % |
| `bms_SOE` | 21 | `0x226` → 55.0 % |

SOH совпадает с `vnsTestApp` (`get_signal_double name[bms_SOH]
value[95.300000] oriValue[3b9]`).

### Почему не `vnsTestApp`

Раньше температуры читались через `vnsTestApp` (команда 1,
`get_signal_double`), а Max предсказывался по Min. Причина: для
`bms_packTempMax` и `bms_packTempAvg` служба `vnsd` пишет в общую память
`raw = -1` (`value[-nan] oriValue[ffffffffffffffff]`), хотя в CAN-кадре
значения есть. Проверено через gdb на
`ProxyLib::TerminalSession::getFixedSignalFromShareMemory`. Сырой кадр через
`vnsMonitorCan` даёт все пять температур одной командой. Константы
`CMD_TEMP_MAX` / `CMD_TEMP_MIN` и `Parsers.parseTemp` оставлены для ручной
диагностики.

### Кадр 0x584 (датчики модулей)

`BMS_moduleTemperature` из `H97.xmls`: мультиплексный кадр, байт 0 — номер
(`datano`), по 6 датчиков на кадр, 9 бит, `°C = raw × 0.5 − 40`.

| Датчик N | datano | startbit |
|---|---|---|
| `bms_moduleXTempSensorN` | `(N−1) / 6` | `9 + 9 × ((N−1) % 6)` |

По описанию датчиков 48, но BMS шлёт только кадры 0 и 1 (~5/с каждый):
живые датчики 1–9, у 10–12 raw `0x1FE`. Кадр читается той же командой, что и
0x304/0x514 (`-s:0x514,0x304,0x584`), `Parsers.parseModuleTemps`. Нет кадра —
`—`, raw `0x1FE`/`0x1FF` — `N/A`. Max/Min по датчикам совпадают с
`bms_packTempMax/Min` из 0x304.

### Кадр 0x574 (изоляция и где Max/Min)

`BMS_tboxRequest` из `H97.xmls`, ~1/с (за 3 с — 1–2 кадра), берётся последний,
`Parsers.parseTboxRequest`:

| Сигнал | startbit | бит | Пример (`34 34 03 08 00 18 4A 00`) |
|---|---|---|---|
| `bms_isolationResistance` | 1 | 16 | `0x3434` → 13364 (factor 1; единица в описании не указана, по величине — кОм) |
| `bms_packTempMinModuleIdx` | 28 | 5 | 1 |
| `bms_packTempMinSensorIdx` | 33 | 3 | 0 |
| `bms_packTempMaxModuleIdx` | 36 | 5 | 0 |
| `bms_packTempMaxSensorIdx` | 41 | 3 | 0 |

Индексы выводятся как есть (с нуля). Соответствие «модуль/датчик» номерам
`T1…T9` из 0x584 пока не установлено.

### drivingCurrentLimit (оценка по bms_packTempMax)

Предел тягового тока батареи передаётся в кадре 0x134 (startbit 1, 14 бит,
`raw × 0.2` А, ~100/с), но **на T-Box этот кадр не приходит**: MCU пересылает
по SPI только ID из своего белого списка (таблица в `mcu/App/block0.bin`,
смещение 0x51378), 0x134 в нём нет — проверено `vnsMonitorCan -all`.

Поэтому значение считается в `Parsers.estimateDrivingCurrentLimit` по
`bms_packTempMax`: таблица с шагом 0.5 °C (25…47.5 °C — из логов, целые А;
48…52 °C — из CAN-дампа, точно), между точками линейно. Ниже 25 °C — 1048 А,
выше 52 °C данных нет — продолжение последнего наклона (−63 А на 0.5 °C), не
меньше 0. На экране — `≈836 А`.

| °C | ≤25 | 30 | 35 | 40 | 45 | 48 | 50 | 50.5 | 51 | 51.5 | 52 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| А | 1048 | 999 | 948 | 894 | 836.4 | 799.2 | 774.4 | 711.4 | 648.2 | 585.2 | 523.2 |

Сверка с реальным 0x134: в установившемся режиме медиана ошибки 0, в 96 %
точек логов — не больше 1 А. Реальный предел после смены температуры меняется
плавно (~2 А / 100 мс), оценка — скачком. Если предел зависит не только от
температуры (SOC, напряжение), оценка этого не учтёт.

## Чтение ячеек

`MainViewModel.refreshCells()` → `SshManager.CMD_CELLS` (≈6 с) — сырые кадры
`0x594 BMS_moduleVoltage`:

```sh
timeout -s INT 6 stdbuf -o0 -e0 /mnt/hirain_app/usr/bin/vnsMonitorCan -s:0x594 2>&1 \
  | grep -a -A1 -F "CAN[594]"
```

### Раскладка кадра 0x594

Из `H97.xmls` (то же в `/mnt/hirain_app/etc/vns/H97/can-in.xml`).
Мультиплексный кадр: байт 0 — номер кадра (`datano`), в каждом по 4 ячейки,
13 бит, `В = raw × 0.001`, нумерация битов как у 0x304.

| Ячейка N | datano | startbit |
|---|---|---|
| `bms_moduleXcellBlockN` | `(N−1) / 4` | `9 + 13 × ((N−1) % 4)` |

Пример: `00 D7 6F FA 55 3F EB 07` → ячейки 1–4: 4.055, 4.051, 4.053, 4.062 В.
Для 90 ячеек нужны кадры 0…22; в кадре 22 ячейки 91–92 — заполнители
`0x1FFF` (8.191), кадр 23 (ячейки 93–96) не передаётся.

### Окно и повторы

Кадры идут ~10/с, полный цикл 0…22 — ≈2.3 с. `vnsMonitorCan` буферизует
вывод сам (не помогают ни `stdbuf`, ни pty через `script`), поэтому выйти
раньше, как только собраны все кадры, нельзя — окно фиксированное. Подписка
после запуска занимает 1…3.7 с, окна 3–4 с не хватает, 6 с обычно
достаточно.

`Parsers.parseCellFrames` берёт последний кадр для каждого `datano`,
`Parsers.cellsFromFrames` собирает напряжения и обрывает список на первом
недостающем кадре. Если ячеек меньше 90, `readCells` повторяет команду
(до 3 попыток), объединяя кадры. Если так и не собрались — статус
«Ячеек: N из 90 — не все кадры 0x594 получены».

Опрос температур на чтение ячеек не влияет: команды идут под одним
мьютексом, а на экране «Ячейки» опрос температур на паузе.

## Запись лога (CSV)

Кнопка «● Запись» / «■ Стоп» в строке статуса экрана «Температуры». Пока
запись включена, рядом показан путь к файлу (красным). Запись идёт в фоне
при любой открытой вкладке (`CsvLogger`, управление —
`MainViewModel.toggleLogging()`).

- **Файл:** новый на каждое включение, `BmsMonitor_yyyy-MM-dd_HH-mm-ss.csv`
  (двоеточие в имени файла недопустимо).
- **Папка:** `Settings.Global` → `bms_log_dir`, если не задано —
  `/sdcard/Download`. Задать: `adb shell settings put global bms_log_dir /sdcard/Documents`.
- **Формат:** разделитель `,`, десятичная точка, время — локальное
  `yyyy-MM-dd HH:mm:ss`. Недействительное значение или нет данных — пустая ячейка.
- **Столбцы (115):** `time, type, temp_max, temp_min, temp_avg, temp_inlet,
  temp_outlet, soh, soc, soe, iso_resistance, max_module, max_sensor,
  min_module, min_sensor, driving_current_limit, sensor_1 … sensor_9,
  cell_1 … cell_90` (`iso_resistance` и индексы — 0x574; `driving_current_limit` —
  оценка по temp_max, А; `sensor_N` — датчики модулей 0x584, °C).
- **Опрос во время записи:** каждый цикл одной командой
  `SshManager.CMD_BMS_CAN_CELLS` (≈6 с) читает кадры 0x304, 0x514, 0x584, 0x574 и 0x594:
  ```sh
  timeout -s INT 6 stdbuf -o0 -e0 /mnt/hirain_app/usr/bin/vnsMonitorCan -s:0x514,0x304,0x584,0x574,0x594 2>&1 \
    | grep -a -A1 -E "CAN\[(304|514|584|574|594)\]"
  ```
  Если кадров 0x594 не хватило на 90 ячеек, добирается командой `CMD_CELLS`
  (всего до 3 попыток). Цикл раз в **10 с** (от начала до начала). Прочитанные
  ячейки показываются и на экране «Ячейки». После «Стоп» — снова только CAN
  раз в 10 с, ячейки читаются только кнопкой «Обновить» на своём экране.
- **Строки:**
  - `bms` — каждый цикл при записи: температуры (°C), SOH/SOC/SOE (%) и 90
    напряжений (В). Время строки — начало цикла; температуры и ячейки
    из одного окна vnsMonitorCan (≈6 с). Пишет только цикл, начатый при
    включённой записи. Пока открыт экран «Ячейки», опрос на паузе — строк
    `bms` нет.
  - `cells` — каждое «Обновить» на экране ячеек: только 90 напряжений.
- Каждая строка сразу сбрасывается на диск. При ошибке записи лог выключается,
  кнопка возвращается в «● Запись».
- **Android:** на Android 11+ приложение создаёт свои файлы в `Download` без
  разрешений. Для Android ≤ 9 в манифесте есть `WRITE_EXTERNAL_STORAGE`
  (`maxSdkVersion 28`), но запрос в runtime не реализован; Android 10 со
  scoped storage не поддержан. Проверено на устройстве с Android 11.

Пример:

```csv
time,type,temp_max,temp_min,temp_avg,temp_inlet,temp_outlet,soh,soc,soe,iso_resistance,max_module,max_sensor,min_module,min_sensor,driving_current_limit,sensor_1,…,sensor_9,cell_1,cell_2,…
2026-10-04 18:35:09,bms,10.5,9.0,10.0,9.0,8.5,95.3,78.1,61.5,13310,1,0,4,0,1048.0,10.0,…,10.5,4.040,…
2026-10-04 18:35:30,cells,,,,,,,,,,,,,,,,…,,4.040,…
```

## Отладка на T-Box

На устройстве нет ssh-клиента, но T-Box доступен с него. С компьютера можно
зайти через adb как через прокси:

```bash
sshpass -p 12345 ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
  -o "ProxyCommand=adb shell -T nc 172.16.104.20 22" root@tbox
```

Полезное на T-Box:

- `export LD_LIBRARY_PATH=/mnt/hirain_app/usr/lib` — нужно для утилит VNS.
- `vnsMonitorCan -s:0x304` — сырые кадры (вывод буферизуется, используйте
  `stdbuf -o0`).
- `/mnt/hirain_app/etc/vns/H97/can-in.xml`, `multi-can-in.xml` — описание
  сигналов.
- `vnsMonitorCan -s:0x594` — напряжения ячеек (см. «Чтение ячеек»).
- На T-Box есть `gdb`, `strace`, `ltrace`.
