# Состав и сборка общего payload

Новый `payload_VERSION.zip` един для USB-установщика и OTA: Native, RestoreMode,
RunYN, root-служба и runtime из `Packaging/new/`. Версия не содержит инфраструктурных суффиксов.
Исходные `Packaging/od/` и `Packaging/pi/` сохранены для прежних релизов.

В manifest используется `infrastructure: unified`, payload schema 4 и recipe
schema 3 / `qinggan-v3`. Общий пакет требует Installer **1.8.1** и capability
`unified-runtime-v1`. Пересборка установщика необходима: добавлены условные пакеты,
новый загрузчик и применение миграции. Старые payload по-прежнему поддерживаются.

## RunYN и определение модели

RunYN присутствует в общем архиве с `condition: except-h97xy`. USB и OTA используют
один `VehicleModel` из release-core: на H97X/H97Y установка RunYN пропускается,
на остальных моделях выполняется. Проверка после установки следует тому же правилу.
На H97X/H97Y уже установленный RunYN автоматически не удаляется.

На разрешённых моделях всегда устанавливается RunYN из payload, включая ту же
или более старую версию. Его versionName/versionCode независимы от версии релиза
и не используются для пропуска установки. При конфликте установленной подписи
USB/OTA полностью удаляют RunYN вместе с данными и один раз повторяют установку
из payload. Package ID, целостность подписи самого APK и хеш файла проверяются.

Проверяются fingerprint, описание сборки, модель, версия IPK и `frombrand`.
Признак H97X/Y имеет приоритет: у исследованной H97X свойство `frombrand` равно H97C.
Модель читается до замены файлов. Выбор OEM-классов хуками выполняется отдельно,
через runtime-адаптеры по доступным классам и методам.

## Миграция и OTA

Сборщик объединяет существующие общие роли приложения/OTA с
`Packaging/new/build/release-inputs.json`. Этот файл генерируется `build.sh`:
новый Go-loader, Frida и агенты размещаются в `/data/local/bin/voyahtune-new/`.
Boot-wrapper использует прежнее имя init-сервиса `voyahtune_load`.

Оба исполнителя применяют тот же recipe: останавливают загрузчик, заменяют файлы,
удаляют прежние loader, Frida, hooks и lock-каталоги по точным путям, затем
перезагружают Android. Перезагрузка обязательна для выгрузки eternalized-хуков.
Накопительный список старых файлов находится в `Packaging/new/config/retired-files.txt`
и общем spec. Отдельного скрипта миграции или второго движка установки нет.

После перезагрузки USB и OTA вызывают `voyahtune-loader --check-hooks`: проверяются
свежесть supervisor, состояния агентов и PID/startTicks целевых процессов. Ожидание
допустимо только без запущенного процесса; отключение — у условных агентов.
Ошибка или незавершённый запуск хука не дают подтвердить успешную установку.

Удаление через установщик очищает старый и новый runtime, включая приватные
каталоги состояния. Это действует и со старым сохранённым recipe, и со встроенным
remover; для его сборки готовый новый runtime не требуется.

Старой root-службе сначала требуется обновление через USB: она не поддерживает
условные пакеты. Совместимая новая служба применяет дальнейшие общие OTA и миграцию
через штатный file executor, сохраняя свой бинарник, init и bootstrap.
Настройки URL каталога и DNS сохраняются; прежний выбор релиза сбрасывается.

`minimumInstallerVersion` первого общего пакета — 1.8.1. `minimumOtaVersion`
задаётся отдельно: базовая версия VoyahTune, впервые содержащая совместимую службу.
Для последующих релизов без замены службы сохраняйте минимум предыдущего
опубликованного общего релиза в выбранном каталоге, определённого по SemVer.
Сборщик требует явный `--minimum-ota-version`, чтобы не подставить старый минимум.

Общий OTA-каталог выбирает версии без суффикса профиля, включая beta. Целостность
архива, manifest, recipe и подписанные runtime-хеши APK проверяются до установки.

## Контракт APK и сборка

Java-база Native/RestoreMode остаётся общей. Её совместимое значение metadata `od`
включает необходимые `acc-hooks`/`driveHookV2`; общий сборщик использует этот контракт.
Внешний manifest и root-служба используют `infrastructure: unified`. Валидатор проверяет эту
пару, версию APK, подписи, точные runtime-хеши и digest recipe. Перепаковка старых APK
с новыми хуками не создаёт полноценного проверенного payload: при выпуске нужны
APK с актуальными подписанными metadata.

Пример первого общего выпуска (номер условный, замените согласованной версией):

```sh
./make_release.sh 4.5.0 --payload --minimum-ota-version 4.5.0
```

Результат: `Releases/dist/payload_4.5.0.zip`, `payload_4.5.0.json` и
`Releases/build/installer-payload-4.5.0/`. GUI собирается отдельно. Публикация —
отдельное действие. Клиенты читают серверный каталог
`https://voyahtune.ru/api/v1/releases`; локальные JSON-индексы не обновляются.

Без сборки APK можно проверить runtime и получить recipe:

```sh
sh Packaging/new/build.sh
cargo run --manifest-path Installer/Cargo.toml -p installer-build -- \
  prepare-unified-runtime --root "$PWD" --output "$PWD/Packaging/new/build/release"
```

Это подготовка файлов и рецепта, а не подписанный payload и не установка на машину.
