# Данные автомобильных карточек приборной панели

Справочник по локальному исследованию от 3 октября 2026 года для нового виджета
VoyahTune. Основная цель — официальные SE и Sport+ 2025–2026, Android 11.
Наличие метода SDK, его реализация и фактическое получение данных на автомобиле
проверяются отдельно. Здесь описана возможность чтения, а не готовая функция VoyahTune.

## Цепочка от знакомой медиакарточки

1. `cluster/display/fragments/ClusterMediaFragment.java:94` создаёт
   `Cluster-Media-Display` и связывает его с категорией `qg.car.cluster.MEDIA`.
2. `instrumentcard/ScreenActivity.java` создаёт медийный `PanelView`.
   В manifest он объявлен с `android.intent.action.MEDIA_SCREEN`.
   Прикладные панели этого APK — медиа, телефон/контакты и темы.
3. VoyahTune использует именно этот дисплей:
   [ClusterMediaHostActivity](../Native/app/src/main/java/ru/big/town/anative/ClusterMediaHostActivity.java).
   Геометрия внедрения 66/200/574/464 при DPI 160 относится к медиакарточке
   простой темы приборки, а не к сетке главного экрана RestoreMode.
4. `cluster/service/InstrumentClusterService.java:570` и
   `service/protocol/voyah/VoyahInstrumentCluster.java:336` обмениваются
   сообщениями с приборкой через `libqg_cluster.so`. В исследованной Java-части
   видны переключение отображаемых областей, медиа/телефон/навигация, настройки,
   тема, единицы и версия IPK. Готового API полного состояния перечисленных
   автомобильных карточек не найдено.

Следовательно, доступ к `Cluster-Media-Display` сам по себе не предоставляет
показания соседних карточек. В этих двух APK не найдены прикладная реализация
карточек расхода/давления и их родная анимация энергии. Предположение о рендере
на стороне IPK согласуется с разделением Android-панелей и сокетного протокола.
Живое исследование ниже подтвердило доступность QNX Neutrino за адресом
приборки; точный процесс рендера и расположение его графических ресурсов
ещё не установлены.

Отдельный доступный путь к части тех же автомобильных показателей — OEM
CanBusService. `canbus/service/CanBusComponentFactory.java:33` выбирает
`DongfengH97CCanBusComponentImpl` для типов 134, H97Y=13401 и H97X=13402.
Прямую связь каждого Android-поля с изображением на приборке ещё надо сверить
по одновременным показаниям; совпадение названий этого не доказывает.

## Доступ для Native

CanBusService экспортирован с action `com.qinggan.canbus.CanBusService`,
package `com.qinggan.canbus.service`; `onBind()` возвращает Binder
`com.qinggan.canbus.ICanBusService`. В исследованных getters статистики нет
проверки WRITE_CANBUS; это отличается от некоторых команд записи. Чтение через
`su 0 service call` на подключённой машине выполнено. Чтение новых полей из
процесса Native отдельно не проверялось; существующее соединение уже используется
для других событий. Root-ответ getter не заменяет проверку callback в Native.

В VoyahTune уже есть единое соединение
[CanBusEventHub](../Native/app/src/main/java/ru/big/town/anative/CanBusEventHub.java).
Оно использует `addCallback` (28), `removeCallback` (29), обрабатывает двери,
КПП, освещение, наружную температуру и VehicleState. Неизвестные callback-коды
сейчас намеренно игнорируются. Для телеметрии надо расширить эту цепочку,
а не создавать вторую подписку или второй reader `/dev/cis_can`.

| Данные | Getter, transaction | Callback, transaction |
| --- | --- | --- |
| Расход для графика | `getEnergyConsumptionPercent`, 79 | `onEnergyConsumptionPercentChanged`, 59 |
| Средние значения и поездки | `getEnergyConsumptionInfo`, 80 | `onEnergyConsumptionInfoChanged`, 60 |
| Давление | `getTPMSInfo`, 70 | `onTPMSInfoChange`, 45 |
| Одометр/запас хода | `getOdometer`, 1 | `onOdometerChanged`, 25 |
| Скорость | `getVehicleSpeed`, 26 | `onVehicleSpeedChanged`, 16 |
| Обороты — кандидат | `getEngineSpeed`, 27 | `onEngineSpeedChanged`, 13 |
| Напряжение — кандидат | `getBatteryState`, 19 | `onBatteryStateChanged`, 26 |

Номера зафиксированы по `canbus/ICanBusService.java` и
`ICanBusServiceCallback.java` версии выше. Это два разных направления Binder;
совпадающие номера в колонках не означают одинаковую операцию. Форматы Parcel
нужно сверить по установленной версии перед реализацией.

`getCanRawData()` не даёт произвольный доступ ко всем CAN-кадрам: в исследованной
ветке H97C `onCanRawData()` вызывается для 0x21A и 0x2FE. Наличие этого getter
не доказывает доступность через него мощности, температур шин или оборотов.

## Уточнение на машине с выбранной карточкой «Поток энергии»

Пользователь выбрал карточку вручную. Через ADB выполнено только чтение:
списки процессов/пакетов/слоёв, хеши, диагностические снимки, известные getters
и уже доступные файлы QNX. Установка APK, перехваты процессов, команды управления
CAN, переключение тем и карточек не выполнялись.

- `screencap -d 4` для физического выхода приборки вернул чёрный кадр 1920×720,
  хотя пользователь сообщил об открытой карточке. Это согласуется с рендером
  вне Android-композиции; один чёрный кадр сам по себе не доказывает архитектуру.
- Слой `cluster_sync_display` — служебный `View` размером 1×1 в
  `ClusterActivity.showPoint()`, а не поток изображения карточки.
- В Android уже смонтированы NFS-ресурсы
  `172.16.104.41:/var → /mnt/qnx/var` и
  `172.16.104.41:/update → /mnt/qnx/update`. Новые mount не создавались.
  Сокет Android Cluster соединён с этим же адресом на порту 80; номер порта
  не означает HTTP: Java/JNI использует собственный протокол.
- Прочитан `/mnt/qnx/var/pps/icm/rx`: есть скорость, передача, её валидность,
  READY, двери и другие статусы; в снятом объекте нет мощности, направлений
  между двигателем/генератором/батареей/колёсами, температур шин или оборотов.
- `/mnt/qnx/var/pps/cluster/linecfg` — конфигурация оснащения;
  `/mnt/qnx/var/data/cardinfo.txt` — последовательность числовых значений
  без доказанной расшифровки. Не использовать их как состояние энергии.
- Прочитан `pps/icm/x5b0`; `x3a9` и `x3ab` при чтении через NFS вернули I/O error.
  Имена файлов не устанавливают содержимое или возможность подписки через NFS.
- Диагностические порты доступны: SSH сообщает OpenSSH 8.5, Telnet —
  `QNX Neutrino (localhost)`. Вход root запросил пароль; пароль не передавался,
  сессия закрыта, команды внутри QNX не выполнялись.
- Скопирован для анализа `IpkUpdateService-release.apk`: штатные интерфейсы
  относятся к обновлению/передаче файлов, готового getter состояния анимации
  не обнаружено. Консольная декомпиляция завершилась с одной ошибкой.
  Упоминаемый там `/data/data/cluster_lang.zip` на машине отсутствует.

После этого пользователь исключил родную анимацию из требований. Извлечение
QNX-ресурсов и дальнейший вход в QNX не продолжаются в рамках этого этапа.
Родная картинка карточки шин также не извлечена; это отдельное ограничение.

### Расход, мощность и история графика

В `canbus/service/protocol/dongfeng_h97c/DongfengH97CCanBusComponentImpl.java`
`dispatchData()` обрабатывает сообщение 115 через `onVCU_stateCha1()`
(`0x3A1`, строки 4091–4215). Условия исключения H97X/H97Y у этой ветки нет.

Декодирование:

- `instantCnsEV`: Intel bits 9..15, `raw - 20`; raw 127 → INVALID=-9999.
  Представимый валидный диапазон −20..106 с шагом 1.
- `instantCnsOil`: Intel bits 58..63, `raw × 0.5`; raw 63 → INVALID=-9999.
  Валидный диапазон 0..31 с шагом 0.5.
- `consumInfoNum`: `(data[4] << 1) | (data[3] >> 7)`; 511 → INVALID.
  На машине прочитан индекс 76. Его шаг и переполнение как координаты пробега
  не проверены, поэтому это пока индекс OEM-выборки, а не одометр в километрах.

Это поля внутри `EnergyConsumptionPercent`, несмотря на название класса.
В Sport+ `app/vehiclesetting/fragments/charge/VehicleSettingService.java:168`
передаёт именно их в `EnergyData.insertEnergyData()`. Разметка
`resources/res/layout/view_energy_chart.xml:49,61` задаёт `kW.h/100km`
и `L/100km`; `EnergyChartView` использует отдельные левую/правую шкалы.
Это подтверждает назначение OEM-графика, но не воспроизводит код карточки IPK.

`EnergyData` хранит историю локально, заменяет последнюю точку при повторном
индексе и интерполирует пропуски. Готового массива всей истории через CanBus
не найдено. В VoyahTune потребуется собственный ограниченный буфер, отдельно
отмечающий пропуски: интерполяцию нельзя выдавать за измеренные точки.

Для запрошенного графика возможны два разных контракта:

- График расхода: зелёная линия в кВт·ч/100 км, синяя в л/100 км, общая ось
  пройденного пути и две подписанные шкалы. Начать с найденных OEM-полей,
  проверив их частоту и координату на машине.
- График мощности со шкалой −40/0/40/80/120 **кВт**: сначала нужен другой,
  подтверждённый сигнал мощности. `кВт·ч/ч = кВт`, но `кВт·ч/100 км` — другая
  величина. Преобразование `P = расход × скорость / 100` допустимо только
  после подтверждения, что оба сигнала мгновенные и синхронные. На стоянке оно
  не восстанавливает потребление. Для бензина нужна собственная шкала;
  л/100 км нельзя подписывать кВт.

Не использовать `PowerLevel.mInstantaneousPowerConsumption` или
`FuelLevel.mInstantaneousFuelConsumption` лишь из-за названия. Первый источник
не прослежен до наполнения H97X; второй при чтении остался 0, тогда как
штатный график явно использует другой класс.

### Поездки: важная экспортная развилка

`onFUEL_info()` (строка 2259, сообщение 143, диагностическая подпись
`0x18,0x69`) заполняет `currentTrip*` и одометр на H97X. Средний бензиновый
расход: byte0 × 0.1, 255 → INVALID. Средний электрический расход:
`u16be(bytes1..2) × 0.1 − 50`, 2047 → INVALID. Пробег текущей поездки:
`u24be(bytes4..6) × 0.1`. Время: `u16be(bytes7..8)`.

`onEnergyConsumptionInfo()` (строка 2130) содержит полноценный декодер
`sinceCharge*`, `sinceReful*` и `sinceTripA*`. Однако его вызов в
`dispatchData`, case 177, ограждён `!isH97OverSea()`.
`isH97OverSea()` (1856) возвращает true для H97X и H97Y. Поэтому наличие этих
getters в общем SDK не означает работающий экспортный источник. Живые
снимки всех соответствующих полей действительно остались UNKNOWN=-1000.
Смена типа автомобиля для обхода этой ветки не является решением виджета.

Для сохранения десятичных знаков использовать объект `EnergyConsumptionInfo`.
Дубли `VehicleState.AVG_FUEL`, `AVG_POWER` и `ODO_THISTIME` в этой ветке
приводятся к int и теряют дробную часть. Поля запаса хода `mEVCruisingRange`
и `mCanTravelMileage` нельзя использовать как электро-км/бензин-км поездки.

Собственная статистика «после зарядки/заправки» потребует подтверждённых
границ периода и накопления энергии/топлива. Простое суммирование средних
расходов, изменение SOC или уровня топлива не заменяют эти измерения.
Надёжный расчёт раздельного пробега также требует определения, как учитывать
смешанное питание. По одному выбранному режиму EV/HEV это не определяется.

[TripStatsService](../Native/app/src/main/java/ru/big/town/anative/TripStatsService.java)
считает время только в Drive, ставит таймер на паузу в P/R/N, завершает поездку
при открытии водительской двери и страхует границу через STATE_ON. Поездки
с суммарным временем в Drive менее пяти минут не записываются в историю. Это не просто время с включения
автомобиля; новый виджет должен либо использовать эту же семантику, либо
явно отличать её от OEM «после запуска».

### Шины, обороты и низковольтная батарея

`onTPMSSystemStatus()` (5092) читает передние колёса из данных `0x411`,
`onTPMSSystemStatus1()` (5106) — задние из `0x421`: позиции 2 и 4 × 0.1.
Это формат данных, поступивших в OEM-обработчик; не универсальная спецификация
всех вариантов физической CAN-шины. Температур эти методы не публикуют.
Все warning-поля снятого `TPMSInfo` равны -1: читаемое давление не доказывает
поддержку предупреждений или отсутствие неисправностей.

В унаследованном `general/CanBusComponentImpl` есть обработчик оборотов
(message 21, u16le) и батареи (message 52, один byte). Но поступление этих
сообщений на H97X не подтверждено. Более того, H97C имеет собственное поле
`mBatteryState`, которое возвращает getter, тогда как родительский обработчик
работает со своим объектом. Нельзя рассчитывать на одинаковое наполнение
getter и callback без отдельной проверки.

`CarSignalService.getVoltageState()` (transaction 37) получает один byte через
MCU ioctl 68; есть callback 19. Полученный 0 может быть кодом состояния.
Его масштаб в вольтах и связь с 12-вольтовым аккумулятором не установлены.
`OBC_CHARGE_VOLTAGE` относится к зарядному устройству и не заменяет 12 В.

### Повторная проверка оборотов при работающем двигателе

3 октября пользователь запустил двигатель и сообщил о показании примерно
800 r/min на приборке. На той же H97X повторены только операции чтения:

- Пять вызовов `service call qg.canbus 27` вернули
  `Parcel(00000000 80000000)`: успешный Binder-вызов с результатом
  `Integer.MIN_VALUE`, то есть `ENGINE_SPEED_UNKNOWN`. В журнале CanBusService
  есть соответствующие сообщения `can not get engine speed.`.
- В установленном Vehicle HAL отсутствует свойство
  `ENGINE_RPM = 291504901 = 0x11600305`. Это подтверждено списком свойств
  `dumpsys car_service` и прямым диагностическим чтением:
  `lshal debug android.hardware.automotive.vehicle@2.0::IVehicle/default --get 291504901`
  ответил `No property 291504901`.
- В повторном снимке доступного QNX `pps/icm/rx` RPM также нет.
  READY и скорость автомобиля не являются оборотами двигателя.
- Найденный в общем SDK `VehicleOnlineState.RPM(180)` относится к
  конфигурации оснащения: `VehicleConfigHelper` извлекает один бит.
  Его нельзя использовать как числовое показание тахометра.
- Проверены дополнительные службы. `dls_vehicle_signal_service` принадлежит
  `dls_reverse_svr` (камера/AVM), диагностика показывает `STATE_HIDE(0)`;
  в изученных интерфейсах `vehicle_stack_service` видны состояния экранной
  службы и callback, отдельный getter оборотов не установлен. Название
  «vehicle signal» само по себе не доказывает наличие телеметрии двигателя.

Прослежена причина результата штатного getter: `mEngineSpeed` изначально null;
`general/CanBusComponentImpl.onEngineSpeedData()` (3328) обновляет его только
при принятом внутреннем сообщении 21 и длине данных не менее трёх байтов.
Число берётся из первых двух байтов little-endian; третий не входит в число.
H97C не переопределяет этот getter. Следовательно, в момент чтения его кэш
не был заполнен этим обработчиком; по одному getter нельзя различить
отсутствие сообщения и его отбрасывание до обновления кэша.

Отдельная подписка не выглядит решением: `addCallback()` вызывает
`BaseCanBusComponent.attachObserver()`, который добавляет Binder-наблюдателя,
но не запрашивает обороты у MCU. `onEngineSpeedData()` сначала обновляет кэш,
затем уведомляет наблюдателей. Получение новых callback на машине пока не
испытывалось, но в исследованном коде они используют тот же источник.

В существующем журнале есть сырые байты сообщения `0x331 MSG_VCU_Rev`
(внутренний case 145). `onMSG_VCU_Rev()` (2069) извлекает из них несколько
режимов/статусов и не публикует обороты. Остальные биты не расшифрованы;
одной контрольной точки ≈800 недостаточно для определения RPM и масштаба.
Этот кадр также не экспортируется через `getCanRawData()` в исследованной
ветке. Журнал не является полным CAN-дампом: отсутствие кадра в logcat
не доказывает его отсутствия на физической шине.

Итог: запуск двигателя не сделал найденные Android API пригодными для
тахометра. Это не доказывает невозможность чтения вообще — приборка получает
показание по своему пути. Для дальнейшего продвижения нужен подтверждённый
декодер её входного сигнала либо сопоставление доступных исходных кадров с
несколькими значениями RPM и переходом двигатель выключен/включён.
Чтение `/dev/cis_can`, вторая CAN-подписка, инъекции/перехваты процессов,
изменение типа автомобиля и диагностические команды записи не выполнялись.

## Подключение к виджету

Предлагаемое расширение, пока не реализовано:

1. Добавить типы событий и декодеры getters/callback в существующие
   `CanBusEventHub` и `CanBusEventRouter`. Сохранять единственное соединение,
   номер сессии, порядок событий и обработку reconnect.
2. В Native собирать снимок телеметрии с источником, временем получения и
   качеством каждого поля: valid / unknown / invalid / stale. Не заменять
   -1000, -9999, `Integer.MIN_VALUE`, `Float.MIN_VALUE` и -1 нулём.
   Наличие нулевого значения само по себе не доказывает живой датчик.
3. Передавать компактный снимок в RestoreMode существующим защищённым
   межпроцессным способом. Начальное чтение делать вне main thread;
   интерфейс обновлять ограниченной частотой, отдельно от входящих событий.
4. Хранить график и необходимые накопители в Native; после разрыва соединения
   показывать пропуск, после сброса/отката одометра начинать новый участок.
   Расходы на стоянке, неподтверждённые единицы и отсутствие данных отображать
   как недоступность, а не как достоверные нули.

Для «текущей мощности» нельзя автоматически использовать ограничения шкалы
как физический предел: выход за −40..120 требует индикатора или адаптации
шкалы, а не скрытого обрезания измерений.

## Геометрия будущего HTML-прототипа

Прототип ещё не создан. Экран 1920×720; геометрию брать из
[MainActivity](../RestoreMode/app/src/main/java/ru/big/town/restoremode/MainActivity.java)
и [activity_main.xml](../RestoreMode/app/src/main/res/layout/activity_main.xml),
с учётом [описания сетки](dashboard-grid.md):

- резерв под левый OEM-док 145dp;
- 12 расчётных колонок и 5 рядов, горизонтальное продолжение сетки;
- padding сетки 6dp, margin каждой плитки по умолчанию 4dp (зазор 8dp);
- верхний системный inset и отдельный вариант полноэкранной сетки;
- при density=1 ширина ячейки `floor((1920−145−4)/12)−8 = 139 px`;
  ширина плитки из N колонок `139×N + 8×(N−1)`;
- высота считается от 720 минус верхний inset и padding сверху, остаток
  распределяется между верхними рядами. DPI и inset не выводятся только
  из разрешения: их нужно явно зафиксировать при прототипировании.

До подтверждения поддержки исходных сигналов макет может демонстрировать
раскладку, но условные числа должны быть обозначены как демонстрационные.
Исключение анимации не означает подтверждения недоступных измерений.

## Проверки и оставшиеся ограничения

Выполнены проверка версий/хешей APK, прослеживание обработчиков H97X,
сопоставление OEM-потребителя графика, чтение Binder-снимков и повторное чтение,
расшифровка Parcel с проверкой количества и типов полей по `writeToParcel`,
проверка Android-слоёв и доступных QNX PPS, проверка локальных ссылок и
`git diff --check`. Исследование не является испытанием виджета или поездкой.

Перед реализацией нужны: сопоставление REV ODO с найденным кандидатом,
проверка динамики/единиц расхода в обычной поездке, частоты callback и смены
индекса графика, границ OEM-таймера, причин INVALID при стоянке. Температуры
шин, напряжение 12 В, обороты, раздельный пробег и статистика после
зарядки/заправки остаются отдельными нерешёнными источниками. Родная картинка
шин не получена; схематический рисунок в прототипе должен быть назван заменой.

Изменена только документация. Сборки и JVM-тесты не требуются, APK не
устанавливались, публикация не выполнялась. **Пересборка установщика не нужна:**
его код, встроенные ресурсы и контракт payload не изменены.
