# Архитектура VoyahTune Installer

Svelte → Tauri commands → `installer-core` → встроенный ADB. Отдельного CLI-процесса
нет. Блокирующая работа выполняется в workers, события библиотеки передаются в Tauri
и в журнал. Cancel и согласие на VoyahHlCTRL — типизированные запросы. Mutex состояния
не удерживается во время ADB/ожидания согласия; busy-state исключает второй запуск
и закрытие окна до безопасной остановки. Аварийное завершение ОС не заменяет rollback:
прерванная установка требует повторной проверки и восстановления.

`session::plan` — общий API диагностики/планирования для GUI и тестов.
`engine::execute` — порядок специальных процедур и файлового recipe.
`plans::classic_steps` описывает те же фазы для UI. `device_commands.rs` содержит встроенные shell-команды автомобиля; общие
helpers находятся в `Packaging/installer/common/`. GUI не запускает host `.sh/.bat`.
На Windows применяется встроенный adb.exe, локальный POSIX shell не требуется.

Desktop по умолчанию получает каталог через `GET https://voyahtune.ru/api/v1/releases`
в [формате каталога релизов](ota-release-format.md). Поле `url` выбранной записи указывает на
`https://voyahtune.ru/api/v1/releases/:id/download`; id не вычисляется из версии.
Архив скачивается по этому URL. Различие номера версии каталога и metadata APK не
блокирует выбор; SHA-256, размер, формат payload и минимум Installer из metadata APK проверяются.
Ранее сохранённый стандартный GitLab URL переключается на backend; пользовательские
и beta-адреса сохраняются. Единая root-служба использует тот же API по умолчанию.

Каталог, requirements, ZIP, SHA-256, распаковка и кэш находятся в `catalog.rs`.
Совместимость проверяется до автомобильных команд. Payload формата 5 использует скомпилированный план установки и по одному Native/RestoreMode APK; RunYN устанавливается по условию модели.
[Контракт](installer-protocol.md).

Новый релиз единый: `make_release.sh` собирает runtime из `Packaging/new/`, общие
Native/RestoreMode и RunYN без выбора инфраструктуры и без суффикса версии.
Manifest использует `infrastructure: unified`; нужен Installer 1.8.2 с capability
`unified-runtime-v1`. Внутренние подписанные metadata APK сохраняют совместимое
значение, которое задаёт общий сборщик. [Контракт](installer-payload.md).

RunYN устанавливается по условию `except-h97xy`. Общий recipe заменяет runtime,
очищает старые компоненты и после перезагрузки проверяет `--check-hooks` нового
загрузчика. Первое обновление несовместимой root-службы выполняется через USB.
Исторические результаты ниже не являются проверкой новых сборок.

Сетевая загрузка в `catalog/download.rs` сохраняет частичный ZIP в
`downloads/partial/<sha256>.part` под общей блокировкой кэша. Повторный выбор релиза,
включая перезапуск GUI, продолжает загрузку по фактическому размеру этого файла.
Запросы HTTP Range получают части до 4 МиБ; каждый запрос ограничен 120 секундами,
подключение — 10 секундами, получение заголовков — 30 секундами. Ограничения
на суммарную длительность скачивания всего релиза нет. Прежний таймаут тела ответа
30 секунд ограничивал весь ZIP, а не паузу между порциями данных.

Обрывы, таймауты и временные HTTP 408/429/500/502/503/504 вызывают до пяти повторов
без продвижения с паузами 1, 2, 4, 8 и 16 секунд. Полученные новые байты сбрасывают
этот счётчик. Во время повторов GUI сохраняет процент и объём загрузки. Отмена
проверяется между чтениями и во время пауз; уже начавшийся блокирующий сетевой
вызов может завершаться до своего таймаута. Ошибки диска и некорректные ответы
не повторяются автоматически.

Ответ 206 принимается только с соответствующими диапазоном, общим размером
и длиной. Если сервер игнорирует Range и возвращает 200, сохранённый префикс
заменяется полным ответом с начала. После получения всех байтов проверяется SHA-256:
неверный файл удаляется, чтобы следующий выбор начал чистую загрузку. Частичный ZIP
не показывается как скачанный релиз и не используется для установки. После успешной
проверки и распаковки файл `.part` удаляется; при отмене или сетевой ошибке сохраняется.
Изменение требует пересборки GUI, но сохраняет версию установщика и требования payload.

Начиная с Installer 1.2.0, первая USB-установка включает root-службу обновлений
и независимый интерфейс. Перед установкой desktop останавливает OTA-службу и сохраняет прежние OTA-логи в отчёт. Подробности —
[устройство updater](ota-updater.md) и [приёмка](ota-acceptance.md).

Файловая блокировка `/data/local/voyahtune-install.lock` не используется:
установщик, OTA и восстановщики не создают, не удаляют и не проверяют её. Остатки
старых установок не препятствуют повторному запуску. Команды после перезагрузки
ограничены Android `timeout` без временного lock; штатный лимит — 180 секунд,
восстановление данных — 1800 секунд. Блокировка запуска приложений на время замены
файлов (`voyahtune-update.block`) сохраняется.

## Подключение и установка

Первый экран выбирает версию VoyahTune, затем установку или удаление. Удаление известно
установщику без полного payload. На компьютере сохраняются recipe и remove-ресурсы
установленных/прерванных релизов отдельно от download cache. Для неизвестных
будущих компонентов нужен соответствующий совместимый payload либо новый GUI.

Пользователь подтверждает единственный подключённый автомобиль. Отсутствие устройства,
несколько устройств, unauthorized/offline показываются до планирования. Код инженерного
меню рассчитывается для даты UTC+8 с возможностью ручного выбора даты.

Plan фиксирует версию GUI, payload/recipe digest, операцию, фазы и recipe.
Backend сохраняет план и выбранный путь; смена содержимого комплекта после проверки отклоняет apply.
Файлы повторно проверяются. Выбор DNS на экране проверки остаётся явным параметром.
API/ABI и inventoryToken служат диагностике и не вводят новые условия совместимости ГУ.

Root/remount, CE/DE, смена подписи, boot transaction/rollback и DNS сохраняют
[прежние специальные процедуры](installer-classic-port.md). Общий recipe заменяет прежний runtime и очищает известные устаревшие файлы.
При том же ключе APK обновляются с сохранением данных. При смене ключа Installer
сначала резервирует данные соответствующего приложения, затем переустанавливает его
и восстанавливает данные. Общий с OTA helper сохраняет CE/DE целиком, включая `shared_prefs`, базы и файлы, и каталоги Android/data,
Android/media, Android/obb в основном эмулируемом хранилище для пользователей с данными
приложения. Заблокированный пользователь, недоступный CE или adopted storage блокируют
удаление: неполный бэкап не допускается. UID и cache GID переназначаются при необходимости,
SELinux-контексты восстанавливаются через restorecon.
Копия хранится в `/data/local/voyahtune-application-backups/<package>` с доступом root;
контрольные суммы проверяются перед повторным использованием и восстановлением.
Перед возвратом данных уже зарегистрированный для пользователя пакет не регистрируется
повторно. Недостающая регистрация восстанавливается без `--wait`: ожидание может зависать
на OEM PackageManager. Вся операция данных ограничена 1800 секундами на ГУ и 1830 на ADB.
При ожидающем восстановлении Native блокировка запуска сохраняется через финальный
reboot и снимается только после возврата данных. Перед снятием блокировки установщик
останавливает `voyahtune_load` и ждёт `stopped`, затем запускает службу заново:
загрузчик, стартовавший под блокировкой, остаётся в необратимом `quiesced`.
Ошибка остановки сохраняет блокировку; повтор после ошибки запуска вызывает `ctl.start`
без повторной остановки уже работающей службы.
Ошибка установки/восстановления сохраняет копию для повторной установки, после успешной
проверки всей установки копия и временные каталоги удаляются. Это резервирование файлов приложения, а не системного Android
Keystore или общих баз PackageManager. Remove не проверяет подписи установленных приложений.
Изменение встроенного поведения требует нового Installer 1.8.7; формат payload не меняется.
Native и RestoreMode APK не резервируются. Прежний runtime не архивируется и не
восстанавливается: сохраняется только существующий permissions XML; резервные копии
иностранных решений обрабатываются отдельными процедурами совместимости.
Известный конфликт VoyahHlCTRL устраняется автоматически в подготовительном шаге:
системная папка сохраняется на компьютере, uninstall выполняется с `-k`, затем идут reboot и продолжение установки.

Остановка runtime допускает уже отсутствующие компоненты: пустое состояние init-службы
означает, что она остановлена; `pkill` с кодом 1 не создаёт предупреждение; пустой список
прежних собственных процессов не передаётся в `kill`. Native runtime сначала
подтверждает quiesce/drain; ошибка завершения запрещает копирование и остановку. Ошибки остановки существующей
службы и остальные ошибки команд сохраняются в диагностике.

## Результаты и упаковка

Events, plan, report и backup сохраняются в каталоге данных приложения на компьютере.
Download cache и recovery — соседние самостоятельные каталоги. Отчёт экспортируется из
GUI, включая идентичность payload при ошибке. Нет нового постоянного mutex на автомобиле.
Старые lock/receipt не используются как право владения устройством.

GUI содержит ADB и небольшой builtin-remover. По умолчанию полного payload нет.
macOS — Universal `.app`, Windows — x64/x86 NSIS, Linux — x64 `.run` (графическая сессия
X11/XWayland, glibc уровня Ubuntu 22.04). Версия всех GUI-пакетов задаётся в `versions.json.installer` и синхронизируется с Cargo/Tauri,
версия ZIP payload — из автомобильного релиза. Сборщик и тестовый драйвер не распространяются.

## Проверки

[Наблюдения предыдущей проверки на ГУ](installer-validation-2026-09-27.md) относятся
к прежнему контракту. Новый релиз требует отдельной проверки на автомобиле.

### История проверки активных APK после USB-установки

GUI сверяет SHA-256 активных Native, RestoreMode и интерфейса Updater с подписанными метаданными APK
выбранного payload после перезагрузки. Путь берётся из `pm path --user 0`, а не
из системного каталога или неактивной записи `dumpsys package`. Одинаковые номера
версии не подтверждают одинаковую сборку: старый APK в `/data/app` может перекрывать
свежий APK в `/system/priv-app` после OTA или ручной установки.

При проверке Updater установщик сначала проверяет регистрацию пакета и наличие
каталогов CE/DE. Для уже готового пакета `install-existing` не вызывается: на
проверке VoyahTune 3.16.0 вызов `cmd package install-existing --wait` зависал при
запущенном Updater и завершался только по ADB timeout. Если регистрации или
каталогов нет, Installer 1.3.0 вызывает `install-existing` без `--wait`, затем
повторно проверяет готовность. Контракт payload при этом не меняется.

Installer 1.3.1 ограничивает время postflight broadcast до 15 секунд на ГУ и
25 секунд для ADB. Если в этот момент перезапустился `system_server`, он проверяет
смену PID, освобождение lock и готовность Android. Если Native уже запущен после
рестарта, повторный broadcast не нужен; иначе он отправляется ещё один раз.
Ошибка без подтверждённого рестарта `system_server` остаётся ошибкой установки.

При установке прежних payload совместимая пересборка Installer 1.5.0 стала различать
неисправную регистрацию Updater и недоступность системных служб. Перед восстановлением проверяются `activity`,
`package`, успешный ответ `pm` и неизменность PID `system_server`. Два согласованных
результата с интервалом две секунды подтверждают состояние; непосредственно перед
изменением пакета оно повторно проверяется под временным lock. Пустой ответ
PackageManager и перезапуск Android не вызывают удаления пакета. Проверка делает
не более 30 попыток и прекращает начинать новые после 90 секунд; отдельные ADB-команды
сохраняют свои тайм-ауты. При подтверждённом сбое служб во время восстановления
установщик возвращается к диагностике, а обычная ошибка команды остаётся ошибкой.
Для исправного пакета `install-existing` по-прежнему не вызывается. Постоянная
недоступность служб или несовпадение активного APK не позволяют завершить установку
успешно. Изменение требует пересборки GUI; версия и требования payload не меняются.
Проверено на fake ADB; проверка этого исправления на автомобиле остаётся отдельным шагом.

Если активный Native или интерфейс Updater отличается, GUI сначала проверяет хеш
системного APK по payload, затем выполняет `pm install -r --user 0` этого файла
под временным lock и повторно сверяет активный APK. Данные приложения сохраняются;
удаление пакета для устранения перекрытия не используется. Ошибка установки,
неоднозначный путь или несовпадение после ответа `Success` блокируют успешное
завершение. RestoreMode устанавливается обычным шагом USB, в конце проверяется
его активный хеш. Эта дополнительная проверка реализована в Rust GUI-движке.

Эта проверка активных APK требует пересборки установщиков macOS и Windows x64/x86,
но сама по себе не меняет контракт payload. В текущем едином payload отдельного
APK Updater нет: экран входит в RestoreMode. Актуальный минимум Installer — 1.8.2.


## Подготовка без дополнительных диалогов

Пятый шаг «Проверка и отключение сторонних решений» выполняется сразу после root,
блокировки операции и монтирования файловой системы на запись, до установки файлов.
Наличие CUNBA/VoyahTweaks больше не блокирует план, применение или проверку запуска.
Установщик записывает `init.logcat.original.sh` в `/system/etc/init.logcat.sh`,
отключает известные пакеты, автозапуск и процессы. Известные файлы перемещаются в
соседние `.voyahtune-disabled*`; копии startup shell хранятся вне каталогов автозапуска
в `/data/local/voyahtune-disabled-loaders`. В общих init rc сохраняются сторонние
по отношению к конфликту службы и действия. Отдельных согласий и повторного выбора
установки нет. Финальная перезагрузка выгружает внедрённые агенты.

После каждой установки проверяется `/data/user_de/0/ru.big.town.anative`.
Если каталога нет, сразу выполняются `am force-stop --user 0`, `pm uninstall -k --user 0`
и `cmd package install-existing --user 0` для Native. Данные сохраняются ключом `-k`;
каталог создаёт Android PackageManager. Проверки хешей и UID не предшествуют этой починке.

Для доставки изменений нужна пересборка Installer. Известные старые журналы восстановления
CUNBA остаются доступны при удалении; автоматический подготовительный шаг их не создаёт.

При удалении GUI проверяет сохранённый журнал Cunba. Если отключение было
подтверждено и резервные данные доступны, на экране плана появляется выключенный
по умолчанию флажок «Восстановить Cunba после удаления VoyahTune». Без согласия
Cunba остаётся отключённой.

После удаления и первой перезагрузки дополнительный шаг проверяет отсутствие
приложений и известных runtime-компонентов VoyahTune, возвращает каталог Cunba,
инжектор и прежнее enabled-state пакета. Из резервной копии возвращается весь исходный `init.logcat.sh`,
с проверкой контрольной суммы и атомарной заменой текущего файла. Занятые пути, изменённые резервные файлы и небезопасные ссылки
блокируют восстановление. Затем выполняется ещё одна перезагрузка и 30-секундная
проверка стабильности Android, возвращённых файлов и состояния пакета. Это не
подтверждение работоспособности всех функций Cunba.

При ошибке удаления восстановление не запускается. При ошибке восстановления
отчёт явно отделяет завершённое удаление VoyahTune от неподтверждённого восстановления
Cunba. Журнал сохраняется; состояния `reactivating` и `restore-reboot-pending`
позволяют повторить удаление с восстановлением после устранения причины. Уже
возвращённые компоненты могут оставаться активными; автоматического повторного
отключения Cunba в этом сценарии нет. После успеха журнал получает состояние
`restored`, повторное предложение восстановления скрывается.

## Сессионный журнал установки

С Installer 1.7.7 выбор действия «Установка» создаёт `sessionId`, отдельный от
`operationId` проверки, отключения Cunba и исполнения плана. Одна сессия охватывает
выбор релиза, подготовку, ошибки проверки автомобиля, DNS, согласия пользователя,
удаление конфликтующих компонентов, Cunba, перезагрузки и проверку служб.
Самостоятельное удаление сохраняет прежний журнал операции; переключение с установки
на удаление завершает установочную сессию ошибкой `ACTION_CHANGED`.

Реализация: `installer-core/src/installation_log/`, команды `log_session_*` Tauri
и регистрация действий в `desktop/src/api.ts`/`App.svelte`. Предварительная проверка
использует `session::plan_with_events`, поэтому её ADB-команды не теряются. События
движка содержат исходный `operationId`; журнал имеет общую последовательность
`sequence` внутри сессии. Отдельно фиксируются `step` (шаги, команды, ошибки),
`user_choice` (решения) и `logcat` (поток устройства и его состояние).

Статусы сессии: `in_progress`, `success`, `error`. Любая ошибка или блокировка проверки
автомобиля сохраняется в `vehicleCheckErrors` и завершает сессию. Конечный экран
GUI завершает её; `finalReason` при ошибке содержит код, сообщение и `displayTitle`,
который использует сам интерфейс. Неподтверждённая готовность, остановка пользователем
и отмена считаются ошибкой, а не успехом. Повтор после конечного результата начинает
новую сессию. Закрытие до результата фиксируется как `USER_CLOSED`; аварийно
прерванная сессия при следующем запуске становится `SESSION_INTERRUPTED`.
Для таких событий без конечного экрана причина описывает жизненный цикл приложения.
Файловый lock не позволяет считать прерванной сессию другого работающего экземпляра.

Сессии находятся рядом с каталогом `operations`, в `installation-sessions/<sessionId>`:
`session.json` — сущность сессии; `logs.jsonl` — полный локальный журнал;
`outbox/*.json` — неизменяемые чанки с локальным смещением журнала;
`delivery-attempts.jsonl` — результаты попыток доставки. «Сохранить отчёт» включает
снимок сессии и outbox. Резервные копии автомобиля в отправляемые чанки не входят.

Локальная упаковка запускается после накопления **100 записей** общего журнала.
Каждый чанк содержит не более 100 записей; logcat и события step/user_choice
попадают в отдельные чанки с общей последовательностью `chunkIndex`.
Таймера нарезки и пустых промежуточных heartbeat нет. События `session-started`
и `session-finished` фиксируют начало и окончание сессии. Автоматически отправляются
только step и user_choice; logcat, включая события подключения и разрывов, остаётся
локально. При успехе, ошибке, отмене или блокирующей ошибке подготовки остаток
упаковывается, а событие завершения отправляется финальным чанком.
Отключение известных сторонних решений входит в общую сессию установки.
Записи не обрезаются.
Чтение среза, сериализация и сохранение outbox выполняются вне блокировки записи
новых событий. Автоматическая доставка выполняется другим потоком: каждый чанк
событий получает одну попытку, тайм-аут HTTP-запроса — 10 секунд. Завершение сессии
останавливает logcat и упаковку, дожидается оставшихся попыток отправки событий
и закрывает отправщик, даже при ошибке сети или сохранения финального чанка.
Автоматических повторов и загрузки старых очередей при запуске нет.

Кнопка «Выгрузить логи» рядом с открытием папки отправляет все события **текущей
установки**, включая logcat. Перед сетевыми запросами фиксируется список неизменяемых
чанков и упаковывается остаток журнала; новые записи не попадают в этот снимок.
Прогресс показывает число подтверждённых пакетов. Первая ошибка останавливает
ручную выгрузку; повтор возможен по кнопке. При повторе сохранённые пакеты имеют
те же идентификаторы и тела запросов, включая уже отправленные автоматически.
Файловый `delivery.lock` исключает две ручные выгрузки одной сессии одновременно;
ручные и автоматические HTTP-запросы выполняются последовательно.

Во время проверки после перезагрузки GUI показывает текущую проверку, причину
ожидания и обратный отсчёт общего 180-секундного срока. После истечения срока
отдельно отображается сбор диагностического отчёта; проверка не считается успешной
по одному лишь окончанию таймера.

Транспорт выполняет HTTPS POST без авторизации:

- `https://voyahtune.ru/api/v1/installation_sessions` — начальный снимок сессии,
  отправляемый сразу после её локального создания.
- `https://voyahtune.ru/api/v1/installation_log_chunks` — чанки со снимком актуального
  состояния сессии; отправка начинается только после подтверждения создания сессии.

HTTP 2xx подтверждает приём; тело ответа не требуется. Остальные статусы, сетевые
ошибки и тайм-ауты считаются неудачной доставкой. Редиректы отключены, TLS проверяется
системным хранилищем доверия, сертификат должен подходить для домена voyahtune.ru.
`Idempotency-Key` содержит `sessionId` для создания сессии и `chunkId` для чанка.
Начальный JSON сохраняется в `session-request.json`, подтверждение — в `session.ack`.
После подтверждения создания повторно отправляются только чанки. Если создание
не удалось, перед очередным чанком транспорт повторяет создание с тем же JSON.
Подтверждение каждого пакета хранится рядом с ним в `.ack`; сохранённые тела
запросов не изменяются.

Серверу нужно устранять дубли по идентификаторам и обновлять сессию из `session`
в чанке, принимая более позднее состояние по `chunkIndex`, без отката финального
статуса из-за запоздавшего чанка. Заголовок идемпотентности требует поддержки на
сервере: потеря ответа после записи может привести к повтору того же запроса.

Форматы запросов:

- [Сущность сессии — JSON Schema](../Installer/schemas/installation-session.schema.json).
- [Чанк с журналом и снимком сессии — JSON Schema](../Installer/schemas/installation-log-chunk.schema.json).

На сервер отправляется поле `request` из локального outbox-файла, без служебного
`journalEndOffset`. `sessionId` присутствует в сущности, чанке и каждой записи;
`chunkId = sessionId:chunkIndex`. В автоматической отправке допустимы пропуски
индексов и sequence: эти записи относятся к logcat и поступают только вручную.
`firstSequence`/`lastSequence` равны null для пустого чанка. Сервер дополнительно
проверяет совпадение sessionId и границ sequence:
эти межполевые ограничения не выражены в JSON Schema.

Logcat запускается отдельным процессом для активной сессии при появлении
одного доступного USB-устройства. Сессия закрепляется за serial. При каждом
подключении используется текущее время устройства и `-T`: старые буферы не читаются.
Из `main/system/crash` сохраняются сообщения VoyahTune/Cunba/Frida, установки
пакетов, загрузки Android, ANR и падений системных процессов. CAN/ADAS, kernel,
audit и посторонний поток мультимедиа не собираются. Та же политика применяется
в единой OTA-службе. События во время отсутствия соединения не догружаются.
Записи содержат host timestamp, boot ID, segment и исходный Android timestamp.
Проверки fake ADB не заменяют испытание USB-перезагрузок на ГУ.
