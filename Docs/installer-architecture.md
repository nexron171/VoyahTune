# Архитектура VoyahTune Installer

Svelte → Tauri commands → `installer-core` → комплектный ADB. Отдельного CLI-процесса
нет. Блокирующая работа выполняется в workers, события библиотеки передаются в Tauri
и в журнал. Cancel и согласие на VoyahHlCTRL — типизированные запросы. Mutex состояния
не удерживается во время ADB/ожидания согласия; busy-state исключает второй запуск
и закрытие окна до безопасной остановки. Аварийное завершение ОС не заменяет rollback:
прерванная установка требует повторной проверки и восстановления.

`session::plan` — общий API диагностики/планирования для GUI и тестов.
`engine::execute` — порядок специальных процедур и файлового recipe.
`plans::classic_steps` описывает те же фазы для UI. `classic_commands.rs` содержит
device-side shell из классических скриптов; GUI не запускает host `.sh/.bat`.
На Windows применяется комплектный adb.exe, локальный POSIX shell не требуется.

Каталог, requirements, ZIP, SHA-256, распаковка и кэш находятся в `catalog.rs`.
Совместимость проверяется до автомобильных команд. Payload schema 3 включает
декларативный recipe и одинаковые Native/RestoreMode APK для Full/Light.
[Полный контракт и матрица режимов](installer-protocol.md).

## Подключение и установка

Первый экран выбирает версию VoyahTune, затем Full/Light/remove. Удаление известно
установщику без полного payload. На компьютере сохраняются recipe и remove-ресурсы
установленных/прерванных комплектов отдельно от download cache. Для неизвестных
будущих компонентов нужен соответствующий совместимый payload либо новый GUI.

Пользователь подтверждает единственный подключённый автомобиль. Отсутствие устройства,
несколько устройств, unauthorized/offline показываются до планирования. Код инженерного
меню рассчитывается для даты UTC+8 с возможностью ручного выбора даты.

Plan фиксирует версию GUI, payload/recipe digest, исходный и выбранный режим, фазы и recipe.
Backend сохраняет план и выбранный путь; смена manifest после проверки отклоняет apply.
Файлы повторно проверяются. Выбор DNS на экране проверки остаётся явным параметром.
API/ABI и inventoryToken служат диагностике и не вводят новые условия совместимости ГУ.

Root/remount, backup, CE/DE, смена подписи, boot transaction/rollback и DNS сохраняют
[прежние специальные процедуры](installer-classic-port.md). Новые согласованные условия:
справочное чтение режима, soft cleanup hooks/Frida перед каждой установкой Light, запись/проверка режима перед финальным reboot.
При том же ключе APK обновляются с сохранением данных; смена ключа сбрасывает только
соответствующее приложение. Remove не проверяет подписи установленных приложений.
VoyahHlCTRL — отдельное согласие на удаление с backup, reboot и повторной проверкой.

Остановка runtime допускает уже отсутствующие компоненты: пустое состояние init-службы
означает, что она остановлена; `pkill` с кодом 1 не создаёт предупреждение; пустой список
принадлежащих комплекту Frida-процессов не передаётся в `kill`. Ошибки остановки существующей
службы и остальные ошибки команд сохраняются в диагностике.

## Результаты и упаковка

Events, plan, mode, report и backup сохраняются в каталоге данных приложения на компьютере.
Download cache и recovery — соседние самостоятельные каталоги. Отчёт экспортируется из
GUI, включая идентичность payload при ошибке. Нет нового постоянного mutex на автомобиле.
Старые lock/receipt не используются как право владения устройством.

GUI содержит ADB и небольшой builtin-remover. По умолчанию полного payload нет.
macOS — Universal `.app`, Windows — x64 NSIS, Linux — x64 `.run` (графическая сессия
X11/XWayland, glibc уровня Ubuntu 22.04). Версия всех GUI-пакетов берётся из Cargo,
версия ZIP payload — из автомобильного релиза. Сборщик и тестовый драйвер не распространяются.

## Проверка на автомобиле

27 сентября 2026 года macOS Universal GUI 1.0.0 с payload 3.13.0 проверен на одном
ГУ Android 11 / API 30, прошивка build 650 (`msmnile_gvmq`). Это не подтверждает
совместимость с другими прошивками или комплектациями.

Подтверждены обновление Full 3.12.0 → 3.13.0, Full → Light и повторный Light.
Пользователь проверил интерфейс Full и Light. При Light отсутствовали все 17 файлов
рецепта, предназначенных только для Full, и процессы loader/Frida; оба приложения
запускались после перезагрузки. Хеши обоих APK совпадали во всех режимах.
83 пользовательских параметра SharedPreferences и файлы DNS сохранились; изменялись
флаг режима и служебные записи состояния hooks/защиты запуска дока.

При первом возврате Light → Full файлы и режим установились, но финальный `am broadcast`
вернул 224 одновременно с перезапуском `system_server`. Причина системного сбоя не
установлена; GUI сохранил ошибочный результат операции. После восстановления Android
приложения и hooks запустились. Отдельная перезагрузка прошла без повторения этого сбоя:
оба приложения запустились автоматически, основные hooks активировались, `system_server`
оставался стабилен во время 90 секунд наблюдения. Это наблюдение не доказывает устранение
первопричины.

После исправления предупреждений macOS GUI повторно восстановил Full: все 17 шагов
завершились успешно, предупреждений и сбросов данных не было. Проверка финального запуска
Native осталась обязательной; ошибка первого прогона не была скрыта повторными попытками
в коде установщика. Установленный payload и APK при пересборке GUI не менялись.
Пользователь подтвердил работу VoyahTune, сплита и дока, а также сохранность настроек
после завершающей установки Full. Автомобиль оставлен в режиме Full 3.13.0.

Сон/пробуждение автомобиля, Windows, смена ключа подписи с очисткой данных и удаление
конфликтующего владельца CAN-разрешения в этой живой сессии не проверялись.
