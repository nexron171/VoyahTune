## Состав приложения

Главный экран — `com.qinggan.app.vehicletype.ui.activity.AirActivity`:
климат, передние и задние сиденья, ароматизация, с условным показом вкладок.
Есть отдельный `AirSecondRowActivity`, редакторы имён памяти сидений и ароматов,
`SeatService`, два варианта `VoiceListenerService` (`ui` и `ui97`).

В прикладных пакетах `com.qinggan.app.vehiclebase.model` и `model97` находятся
контроллеры климата, автомобиля и сценариев, обработчики голосовых команд,
память сидений/зеркал, интеграция TSP и DataCenter. Включённые библиотеки
медиа, карт и общие перечисления CAN сами по себе не означают отдельной
доступной функции этого приложения.

Manifest также декларирует `BLEControlService`, однако соответствующий класс
не обнаружен среди выгруженных Java-исходников. Рабочий BLE-интерфейс этим
исследованием не подтверждён.

## Внешние точки входа

Manifest и `AirActivity.initData/onNewIntent` подтверждают следующие actions:

| Action | Экран |
| --- | --- |
| `com.qinggan.app.vehicle.SHOW_AIR` | Климат |
| `com.qinggan.app.vehicle.SHOW_SEAT` | Передние сиденья; при отсутствии вкладки — доступная задняя |
| `com.qinggan.app.vehicle.SHOW_FRAGRANCE` | Ароматизация |
| `com.qinggan.app.vehicle.show.secondrow` | Отдельный экран второго ряда |

Это кандидаты для кнопок/голосовых переходов VoyahTune. Первые три обрабатывает
`com.qinggan.app.vehicletype.ui.activity.AirActivity`, четвёртый объявлен для
`AirSecondRowActivity`. Activity с intent-filter не имеют явного exported;
для данного targetSdk применяется старое поведение Android. Разрешение запуска
и фактическое наличие вкладки нужно проверить на целевой прошивке через
PackageManager и пробный запуск. Не считать action командой включения климата.

Пример ручной проверки открытия, не выполненной в ходе исследования:

```sh
adb shell am start -a com.qinggan.app.vehicle.SHOW_AIR -p com.qinggan.app.vehicle
```

`VoiceListenerService.onBind()` возвращает `null`; в manifest голосовые службы
не объявлены exported и не имеют intent-filter. Готовый публичный Binder API
«выполнить любую автомобильную команду» здесь не обнаружен. Службы регистрируют
обработчики в OEM ControlManger/VuiServiceMgr. Подменять их или запускать вторую
копию для VoyahTune не требуется.

### Важные детали протокола

- `AirConditionControl.setLeftTemp/setRightTemp/setBackTemp` ограничивают значение
  диапазоном 15.5–30.5 и вызывают `setAirConditionStateEx`. Включённый
  `CanBusManager.setAirConditionStateEx` умножает float на 10: например, 22.5 → 225.
  Это диапазон данной обёртки, не доказательство диапазона для всех прошивок.
- Скорость вентилятора эта обёртка ограничивает 1–8; выключение вынесено отдельно.
- `setVehicleAndAirConditionBundleState` получает сначала **air**, затем
  **vehicle** bundle. Ключи — имена enum, полученные через `name/toString`.
- Нельзя переносить все команды как «0 выключить / 1 включить»:
  `AirSetDialog.checkTempDown` и `turnIonDown` отправляют 1 в обеих ветках,
  а DOR-переключатель отправляет 1 лишь при расхождении желаемого и текущего
  состояния. Это признак toggle-семантики; её следует подтвердить на сервисе.
- В `SmartControl` соседствуют температуры 32/15 и 260. Поэтому копировать
  bundles сценариев без проверки единиц измерения и платформенной ветки нельзя.
- `VehicleControl.setVehicleState` игнорирует возвращаемое значение
  CanBusManager и возвращает 1 после вызова. Это не подтверждение ни успешной
  передачи, ни физического исполнения. Сам CanBusManager возвращает 0 после
  Binder-вызова и -1 при ряде ошибок.
- `CanBusTool` принимает `onAirConditionChanged`, `onVehicleStateChanged`,
  `onSeatAdjustStateChanged`, `onVehicleStateSettingResponseEx` и другие callbacks.
  Это основание для синхронизации UI с OEM-событиями; конкретный смысл ответа
  и связь с физическим выполнением требуют проверки для каждой операции.

## Оснащение и ограничения платформы

`SupportUtils` использует `VehicleConfigHelper.readOnlineConfigItem`:
`DSH/PSH` — передний подогрев, `DSV/PSV` — вентиляция,
`DSMass/PSMass` — массаж, `DSMemory/PSMemory` — память,
`SWC_HEAT` — обогрев руля, `AIR_FCM` — ароматизация, `ION` — ионизация,
`ASC` — пневмоподвеска, `GLASS_HEAT` — обогрев стекла.

Особенно важно: не все поля означают «1 = поддерживается». Для `RSH` ветка
97C проверяет 1, другая — 0; `RSV/RSMass/RSR` в этом helper проверяются на 0.
`VehicleConfig` также по-разному трактует тип силовой установки для веток
(extended: 3 и 1). Универсальный булев адаптер по ненулевому значению неверен.

`APPUtils` делегирует определение H56/H97 и подвариантов в AppCommonUtils.
`StartServiceListener` запускает `ui97.VoiceListenerService` при IsH97 и
`ui.VoiceListenerService` при IsH56. Без чтения конфигурации конкретного автомобиля
не следует выбирать ветку по названию файла APK.

Память сидений — не просто setter: участвуют локальные позиции, account ID,
DataCenter/TSP, Settings.Global, координаты зеркал, таймауты и обратные события.
В `SeatMemoryManager.isDriving` есть ограничение `getVehicleSpeed() > 5`;
это условие штатной реализации, а не рекомендация разрешать перемещения
кресла на ходу в VoyahTune. Единицы/масштаб скорости отдельно не исследовались.

## Практическая польза для VoyahTune

1. **Быстрые переходы в штатные экраны.** Добавить действия «Климат», «Сиденья»,
   «Ароматизация» через перечисленные Intent actions, с проверкой доступности.
   Это наиболее простой кандидат для следующей реализации.
2. **Климатическая карточка и голосовые команды.** Использовать актуальные
   значения `AirCondition` и OEM setters для температуры, вентилятора, AUTO,
   рециркуляции и обдува. В существующем `VoiceOemTransport` загружается
   `VehicleState`; `AirConditionState` потребует осознанного расширения API,
   а не подстановки имени поля в существующую команду сиденья.
3. **Таймер ароматизации.** В `FragranceRestorePolicy` уже есть switch,
   вкус и интенсивность. APK подтверждает их поля (774/775/777) и даёт
   дополнительный кандидат `FCM_DURATION_CONTROL(1067)` на 30/60/без ограничения.
   Применимость новой команды на SE/Sport+ пока не подтверждена.
4. **Учитывать реальное оснащение.** Можно скрывать неподдерживаемые карточки
   и команды по OEM-конфигурации, сохраняя платформенные различия и состояние
   «неизвестно», если конфигурация недоступна.
5. **Память кресел/зеркал.** Возможны именованные действия восстановления,
   но сначала нужно воспроизвести всю последовательность и ограничения,
   а не отправить только `DMS_GET_MEMORY_REQ`.
6. **Подтверждение состояния.** Использовать уже имеющийся `CanBusEventHub`
   и `OemVehicleStateTransport`, расширяя обработку нужных событий.
   Не вводить второй параллельный raw CAN-транспорт.

Сиденья, окна/люк и ароматизация частично уже реализованы в VoyahTune:
сопоставлены `OemCommandSender`, `VoiceOemTransport`, `FragranceRestorePolicy`,
`OemVehicleStateTransport`, `CanBusEventHub` и [каталог голоса](voice-commands.md).
Поэтому APK полезен не только для новых функций, но и для проверки значений,
платформенных условий и поведения существующих команд. Новые функции в ходе
этого исследования не добавлялись.

Наличие PM25-полей, классов BLE, общих enum ADAS, зарядки или задних кресел
не подтверждает наличие соответствующего оборудования/датчика на машине.
Показания датчиков этим исследованием не измерялись.

## Проверка и дальнейшее применение

Выполнены распаковка/декомпиляция, проверка manifest/BuildConfig/SHA-256,
сопоставление прикладных вызовов с включённым SDK и кодом VoyahTune.
Перед внедрением конкретной функции нужны проверка установленного OEM API,
определение комплектации и ограниченный тест с наблюдением обратного состояния.
107 ошибок JADX ограничивают полноту исследования; спорные методы следует
перепроверить по DEX/smali и реализации установленного CanBusService.

Изменена только документация. Сборка APK и тесты приложений не требуются;
установка, проверка на автомобиле и публикация не выполнялись.
**Пересборка установщика не нужна:** исполняемый код, ресурсы и контракт payload
не изменены.
