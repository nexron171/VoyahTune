# Выбор и сохранение станции RdsApp

В VoyahTune реализовано сохранение и восстановление через клиентский перехват
в процессе RdsApp. Описание реализации находится в конце документа;
разбор исходного OEM-приложения ниже относится к APK без этого перехвата.

## Объект и границы исследования

Статический анализ от 2026-09-30: `rdsapp-release-signed.apk`, пакет
`com.pateo.rdsapp`, versionName `1.0`, versionCode `1`.
SHA-256: `36b4d73a889aa78325f6a6ff0c8113c6b13605620a5a4b045209fbff36449cca`.
Локальная декомпиляция JADX 1.5.3 находится в
`tmp/car_apks/rdsapp-jadx`; этот каталог может отсутствовать в другом checkout.
Класс `RdsManager` дополнительно декомпилирован из указанного APK для сверки
основных выводов. Ни установка, ни испытания на машине не выполнялись.
Происхождение APK с конкретной комплектации/прошивки не установлено.

В APK присутствует клиент OEM API, но не реализация внешней службы
`com.adayo.service.dab` (`adayo.dab`). Поэтому анализ показывает, что делает
приложение, но не доказывает сохранение частоты или избранного после отключения
питания на SE/Sport+ либо других комплектациях.

## Как выбирается станция

Пути ниже приведены относительно `tmp/car_apks/rdsapp-jadx/sources/`.

1. Нажатие строки в `com/pateo/rdsapp/main/widget/listInfo/RadioInfoAdapter.java`
   вызывает `RdsDataModel.playStation(station)`, затем `setPlayList(...)`.
   Нажатие уже играющей станции ставит воспроизведение на паузу.
   `main/widget/play/PlayViewAdapter.java` также выбирает объект `RadioStation`.
2. Ручная шкала в `main/widget/play/PlayView.java` вызывает
   `RdsManager.playRadio(freq, isFM)`: создаётся `RadioStation`, задаются диапазон
   и `isRDS=false`, после чего вызывается `playStation`.
3. `com/pateo/overSideRadio/base/dab/RdsManager.java`, метод `playStation`,
   запрашивает OEM-аудиофокус, проверяет готовность и окончание сканирования,
   переключает источник. Если источник ещё не переключился, команда откладывается
   до события `onCurrentResource` через `actionCode=1002` и `tempPlayStation`.
4. `PateoDabManager.playStation` передаёт
   `DABManager.getInstance().playRadio(isFM, piOrFreq, hasRDS, lastAF)`.
   Для RDS `piOrFreq` — PI-код, иначе частота; `lastAF` получает частоту.
5. `com/adayo/proxy/dab/DABManagerImpl.java` пересылает вызов через Binder
   в `IDABServiceInterface.playRadio`. Это команда без возвращаемого результата;
   факт её отправки не является подтверждением настройки тюнера.
6. Полученное от OEM событие `onCurrentStationUpdate` обновляет `curStation`
   и слушателей интерфейса/медиасессии. События `onCurrentFMFreq` и
   `onCurrentAMFreq` обновляют поле `freq`.

Следующая/предыдущая станция выбирается по текущему `playList`, с переходом
через край списка. Состав списка зависит от FM/AM, избранного и PTY;
индекс не является устойчивым идентификатором станции.
`RadioStation.getFreqText()` делит внутреннюю частоту на 100 для отображения FM:
например, 10170 соответствует 101,7 МГц. Сохранять следует исходное целое значение
и диапазон, без повторного разбора отображаемой строки.

## Что сохраняется

| Данные | Поведение исследованного приложения |
| --- | --- |
| Текущая станция и частота | `curStation` и `freq` находятся в памяти; собственной записи этих полей на диск в исследованном тракте нет. |
| Настройки списка | `setPlayList` записывает `SP_PLAY_DATA` в SharedPreferences `RdsManager`. JSON содержит только `playType` и `ptyCode`, без частоты и PI. |
| Чтение настроек списка | `getPlayData()` просто возвращает `new RdsPlayBean()`. Сохранённый JSON не читается; наличие `buildRdsSpBean` само по себе не означает его использование. |
| Станция при запуске | `initData()` получает её через `PateoDabManager.getCurRadioStation()` → `DABManagerImpl.getCurrentRadioStation()` → внешняя OEM-служба. Затем заново задаёт тип списка FM/AM. |
| Избранное | `setFavStation` вызывает OEM `setFavoriteRadio(freq, isFM, favorite)`; списки читаются через OEM API. Долговечность хранения в службе по этому APK неизвестна. |
| Переключатель PTY | `SP_PTY_STATE` действительно записывается и читается через SharedPreferences. |

`SpUtil` использует `Context.getSharedPreferences(name, 0)` и `apply()`.
Ожидаемое расположение для пользователя 0:
`/data/user/0/com.pateo.rdsapp/shared_prefs/RdsManager.xml`
(обычный эквивалент — `/data/data/com.pateo.rdsapp/shared_prefs/RdsManager.xml`).
Это вывод из кода, файл с машины не получен.

`play()` в нижнем слое вызывает `audioPlay()`, `resumePlay()` — `resumeSource()`.
Они не восстанавливают частоту из локальной записи RdsApp.

Вывод: у RdsApp нет подтверждённого собственного механизма долговременного
сохранения последней станции. При запуске он полагается на OEM-службу.
Утверждать, что автомобиль вообще не сохраняет станцию, по одному APK нельзя.
Исправление только чтения `SP_PLAY_DATA` восстановит настройки списка,
но не последнюю частоту.

## Возможные способы восстановления

### Через медиасессию RdsApp

В манифесте экспортирована служба
`com.pateo.midrds.media.RdsMediaBrowserService`; `onGetRoot` возвращает корень
без собственной проверки клиента. Доступность с Native на машине ещё не проверена.
`RdsPlayer` публикует метаданные с частотой, диапазоном и названием станции.
Можно сохранять подтверждённые метаданные в Native, затем получать актуальный
список через `MEDIA_ACTION_GET_CURRENT_RDS_PLAY_LIST`, находить пару
«диапазон + частота» и вызывать custom action `COMMAND_PLAY_BY_INDEX` с `DATA_INDEX`.
Эти три строковых значения сверены с `MediaConstants.RdsCommand`
исследованного APK и совпадают с именами констант.

Этот путь сохраняет обработку аудиофокуса внутри RdsApp, но зависит от наличия
станции в текущем списке. Порядок и фильтр списка могут меняться; нельзя хранить
только индекс. Между чтением списка и выбором возможна гонка — нужен контроль
полученных метаданных. Прямого выбора произвольной частоты в обработчиках этой
медиасессии не найдено; `onPlayFromMediaId` пустой. `COMMAND_SET_RDS_FAV`
с частотой меняет избранное, а не настраивает тюнер.

### Через OEM API из Native

Сохранять подтверждённую станцию по OEM callback, восстанавливать через тот же
`DABManager`/Binder-транспорт, которым пользуется RdsApp. Формат записи:
версия схемы, диапазон, целая частота, признак RDS, PI-код при наличии и время
подтверждения. Возможность соединения, разрешения и соответствие AIDL конкретной
прошивке требуют проверки. Не нужно создавать отдельный CAN-транспорт.

Этот путь позволяет восстановить частоту, которой нет в списке. Вместе с тем
прямой `playRadio` обходит аудиофокус и ожидания, реализованные в `RdsManager`;
их необходимо согласовать с OEM-медиасистемой. Это возможный вариант
для будущей реализации без перехвата; в текущем решении выбран вызов внутри
RdsApp, чтобы сохранить его обработку аудиофокуса и переключения диапазона.

### Исправление или перехват внутри RdsApp

Добавить запись станции в `onCurrentStationUpdate` и восстановление после
готовности OEM-службы через существующий `RdsManager.playStation`.
Это сохраняет штатную обработку аудиофокуса и переключения источника.
Патч APK затрагивает подпись и обновление OEM-приложения; перехват зависит
от конкретных классов и версии. Этот вариант требует сопровождения каждой
поддерживаемой версии и отдельной проверки механизма загрузки перехвата.

### Проверка сохранения в самой OEM-службе

Получить APK/реализацию `com.adayo.service.dab` и исследовать запись последней
станции, восстановление и обработку выключения питания. Возможно, механизм
уже существует, но сбрасывается или не вызывается. Самостоятельная запись
частоты в XML RdsApp этого не исправит: в найденном коде нет её чтения.

## Правила будущей реализации и проверки

- Сохранять подтверждённое состояние, не только нажатие кнопки или отправленную
  команду. Отфильтровывать промежуточные частоты при сканировании и прокрутке.
- На старте сначала загрузить сохранённое значение и дождаться готовности службы;
  не затирать его стартовой/временной частотой до решения о восстановлении.
- Восстанавливать один раз в рамках подходящего события, отменять при новом выборе
  пользователя. Не включать радио поверх выбранного другого источника или звонка;
  выбранная станция и разрешение возобновить звук — разные состояния.
- Подтверждать результат callback/повторным чтением, ограничивать повторные попытки.
- Проверить отдельно перезапуск RdsApp, перезапуск головного устройства,
  цикл ACC и полный сон/обесточивание; фиксировать до и после частоту, диапазон,
  текущий источник и избранное. Переживание перезапуска приложения не доказывает
  сохранение после отключения питания.

## Реализация в VoyahTune

[app_client.js](../Packaging/inject/app_client.js) содержит отдельный обработчик
точного пакета `com.pateo.rdsapp`. Он устанавливается на основном потоке после
`Application.onCreate`, чтобы не инициализировать `RdsManager` до готовности
`BaseApplication.mContext`. Поиск объектов через `Java.choose` не используется.
Штатный обработчик геометрии остаётся доступен, если пользователь отдельно
выбрал для радио полноэкранный режим.

[Загрузчик](../Packaging/system/load.bin) обнаруживает уже запущенный основной
процесс RdsApp в обычном app-client worker, независимо от настроек DPI и
полноэкранного режима. Он не запускает приложение сам. Сохраняются проверки
identity процесса, Android-пользователя 0, ABI `app_process64`, одна попытка
на экземпляр процесса и защита от частых перезапусков. Готовность требует
одновременно `[app-client] hook ready v1` и `[rds-restore] hook ready v1`.
Неподдерживаемые классы/сигнатуры приводят к откату частично установленных
радио-перехватов и сохранению штатного поведения.

### Сохранение

Отдельные SharedPreferences `voyahtune_rds_restore`, ключ `station`, содержат
одну JSON-запись schema 1: диапазон `fm`, целую частоту `freq`, признаки `rds`,
PI-код `pi` и признак временного TA-состояния `ta` (записывается только false).
Для пользователя 0 это обычно файл
`/data/user/0/com.pateo.rdsapp/shared_prefs/voyahtune_rds_restore.xml`.
OEM `SP_PLAY_DATA` не изменяется.

Новая станция принимается после явного `playStation` и совпадающего OEM-состояния.
После 750 мс повторно проверяются текущая станция, готовность и отсутствие
сканирования/TA. Используется одна запись через `commit()`; ошибка записи не
заменяет прежний сохранённый снимок в контроллере. Одинаковые события не вызывают
постоянных записей. Пауза сразу после подтверждённого выбора не теряет этот выбор.

При первой установке без сохранённой станции можно запомнить стабильное текущее
OEM-состояние. При последующих запусках произвольная стартовая частота не заменяет
сохранённую. Разрешено обновление частоты той же RDS-станции с совпадающим PI
(AF). Промежуточные частоты сканирования и временные TA-станции не записываются.
После явно начатого поиска можно сохранить подтверждённый конечный результат;
при отсутствии FINISH режим ожидания поиска снимается через 60 секунд без
изменения сохранённой станции. Неизвестная будущая схема записи сохраняется
нетронутой, радио-перехваты не устанавливаются.

### Восстановление

Триггеры: `RdsManager.play`, `resumePlay`, кнопка UI `RdsDataModel.play`, а также
OEM-событие активного радио или повторная инициализация при уже играющем радио.
Для автоматического пути одновременно проверяются RDS-источник, состояние
воспроизведения и принадлежность аудиофокуса радио; повторные события одной
фазы воспроизведения не создают новые попытки. Сам attach и включение экрана
ничего не воспроизводят.

Контроллер использует штатный запрос аудиофокуса сразу при запросе восстановления.
Поэтому переключение на другой источник во время ожидания готовности не должно
привести к позднему захвату звука обратно. Звонок или потеря фокуса отменяют
ожидание. Готовность и подтверждение проверяются каждые 250 мс в пределах одного
10-секундного запроса. Отправка настройки выполняется максимум один раз за
этот запрос; бесконечного переустановления станции нет.

Для настройки создаётся `RadioStation`, затем вызывается оригинальный
`RdsManager.playStation`. Его OEM-транспорт, обработчик аудиофокуса и ожидание
смены источника сохраняются. Только во время собственного восстановления AM
исправляется обнаруженная в RdsApp 1.0 ошибка: ветка AM в `playStation` запрашивает
FM вместо MW. Если станция уже совпадает, повторной настройки нет; явное
возобновление включает звук через штатный `play`, автоматическое событие уже
играющего радио не посылает лишний `play`.

Явный выбор новой станции, поиск, пауза или потеря фокуса отменяют восстановление.
Удаляются только отложенные OEM-объекты, принадлежащие этой попытке; более новые
пользовательские команды не очищаются. Временная OEM-пауза при смене диапазона
с сохранённым фокусом не уничтожает уже отправленную настройку. Готовность,
отправка и подтверждение станции — отдельные состояния; таймаут не выдаётся за
успешное восстановление.

### Диагностика, ограничения и выпуск

Logcat: `VoyahRdsRestore` (`station saved`, `restore submitted`,
`restore confirmed`, причины отмены/таймаута). Лог установки:
`/data/local/tmp/voyahtune_app_client.com.pateo.rdsapp.txt`, рядом `.pid`,
`.attempt`, `.history`, `.blocked`. Общий публичный hook-status не расширен.

Реализация ориентируется на исследованный RdsApp 1.0. Локальные тесты не
подтверждают работу на конкретной SE/Sport+ и не доказывают слышимое воспроизведение.
Нужны испытания после перезапуска приложения/ГУ, ACC и полного сна, а также
проверки звонка, другого источника, FM/AM, ручной шкалы, поиска, AF/TA и ошибок
OEM-службы. 32-битный процесс текущим app-client loader не поддерживается.
Поздний attach может пропустить уже выполненный выбор или автоматическое
возобновление; сохранённая станция тогда применяется при следующем подходящем
запросе/событии. Изменения станции сторонним клиентом напрямую в OEM-службе
не считаются явным выбором в RdsApp и не должны молча перезаписывать его снимок.

Тесты политики и настоящих Frida-адаптеров с моделью OEM:
`node Packaging/tests/test_rds_restore.js` (38 сценариев). Они включены также
в существующий `sh Packaging/tests/test_app_client.sh`, который запускает
релизная проверка. Shell-loader проверяется
`python3 Packaging/tests/test_parallel_hook_loader.py` (23 сценария, из них 6 RDS).
На macOS этому тесту нужен доступ к `ps` и сигналам собственным дочерним процессам.
Проверены также MapKit, pipe-records и ограничение повторов loader.

Изменены существующие `app_client.js` и `load.bin`; оба уже входят в payload.
Новых операций recipe, встроенных ресурсов recovery/remover и изменений
исполняемого установщика нет. Пересборка GUI и повышение его версии не нужны;
для выпуска требуется новый payload по обычному [релизному процессу](releasing.md).
На работающем автомобиле новый агент начинает действовать в новом процессе
RdsApp/после предусмотренной обновлением перезагрузки. Удаление VoyahTune
убирает загрузчик/скрипт, но не очищает данные штатного RdsApp; запись остаётся
неактивной до следующей установки перехвата. Уже внедрённый агент живёт до
перезапуска процесса/ГУ. Установка, публикация и испытания в этой задаче не выполнялись.
