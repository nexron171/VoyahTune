# Расход топлива: дополнительное офлайн-исследование

Продолжение исследования от 3 октября 2026 года, без подключения к автомобилю.
Исходная проблема: приборка показывала средний бензиновый расход около
4–5 л/100 км, а Android `EnergyConsumptionInfo` возвращал INVALID.
Версии машины, APK и предыдущие захваты описаны в
[основном исследовании телеметрии](oem-cluster-telemetry.md).

**Новый подтверждённый источник среднего бензинового расхода пока не найден.**
Проверены расширенный payload статистики, дополнительные OEM-интерфейсы,
нерасшифрованные MCU-сообщения и кандидаты накопленного объёма топлива.
Есть отдельный OEM-запрос для будущей проверки, но его штатный декодер
содержит подозрительную арифметику, подтверждённую по DEX.

## Расширенный `FUEL_info`: расход не обнаружен в хвосте

Повторно проверены исходные payload, а не только результат Java getter:

| Источник | Записей | Длина payload | Байт 0 среднего бензинового расхода |
| --- | ---: | ---: | --- |
| Netlink, окно 30 с | 13 | 28 | `FF` во всех |
| Netlink, первое окно 55 с | 22 | 28 | `FF` во всех |
| Netlink, 55 с при подтверждённо работающем ДВС | 6 | 28 | `FF` во всех |
| MCU, команда `0x1869` | 25 | 26 | `FF` во всех |
| OEM logcat, после удаления повторов по времени и payload | 48 | 28 | `FF` во всех |

Источники частично перекрываются: складывать строки таблицы как число
независимых измерений нельзя. MCU-журнал охватывает пробег поездки
35,1–36,1 км; весь этот журнал не привязан к подтверждению включённого ДВС.

Байты нумеруются с нуля. H97X-декодер использует b0 для среднего бензина,
b1–b2 для среднего электричества, b3 для средней скорости, b4–b6 для
дистанции поездки, b7–b8 для времени; далее находятся одометр и запасы хода.
Неиспользуемые им b20–b21 **во всех проверенных записях совпали с b24–b25**,
которые OEM публикует как `mCanTravelMileage_real`. В разных окнах это
196–219 и 283–284, а не отдельный найденный расход. b26–b27 в 28-байтовых
записях всегда `00 00`. Это наблюдение о конкретных записях, не полная
спецификация расширенного формата.

Поиск чисел, похожих на 4–5, даёт ложные совпадения. Например, в MCU
`FUEL_info` b3=42–46; деление на 10 дало бы 4,2–4,6, но OEM использует
этот байт как **среднюю скорость**. b8=45–50 — часть времени поездки.
Переназначать такие поля среднему бензину нельзя.

## Getters не включают передачу расхода

В H97X `getEnergyConsumptionInfo()` и `getEnergyConsumptionPercent()`
просто возвращают сохранённые объекты. Они не отправляют MCU-запрос.
В исследованном OEM VehicleSettings Sport+ 13.1 экран поездки читает эти
getters и подписывается на callback, а `VehicleSettingService` сохраняет
точки графика из `onEnergyConsumptionPercentChanged()` в локальный
`EnergyData`. Отдельной команды включения передачи расхода в этой цепочке
не обнаружено. Частый опрос того же getter не создаст новый источник.

`getInstantFuelConsumption()` в H97X возвращает целую часть
`mFuelLevel.mInstantaneousFuelConsumption`, а
`getComprehensiveFuelConsumptionEX()` — `mFuelLevel.mAvgFuelConsumption`.
Это те же поля, чьи обработчики наполнения не имеют найденных вызовов
в исследованной H97C-декомпиляции; самостоятельным источником они не стали.

В общем SDK есть номера `CAN_MSG_FUEL/HISTORY/HISTORY_15/MINUTE` 36–39,
но исследованный общий dispatch их игнорирует. В трёх Netlink-окнах они
также отсутствуют. Сообщения статистики H97C 177/178 и топливный
`FUEL_INFO` общего протокола 49 не наблюдались.

## Ещё один OEM-путь: `requestTravellingInfo`

В сервисе найден отдельный запрос, не используемый рассмотренным экраном
OEM-статистики:

```text
ICanBusService.requestTravellingInfo(AvgConsumptionSinceStart)
  Binder transaction 63
  → general.CanBusComponentImpl.requestTravellingInfo()
  → FillCommand(10, [19, 0], 2)
  → sendCanIOCtl(0, ...)
```

У H97X нет переопределения этого метода. Общий dispatch принимает внутреннее
сообщение **45** и вызывает `onTravellingInfoData()`, которое отправляет
callback `onTravellingInfo`, transaction **38**. В имеющихся Netlink-окнах
сообщений 45 нет; сам запрос на машине в этом исследовании не выполнялся.
Наличие кода подтверждает путь отправки запроса, но не поддержку MCU.

Детали, которые нельзя смешивать:

- `AvgConsumptionSinceStart` имеет ordinal **3**, value **48**;
  Parcelable пишет оба числа.
- Для этого запроса Java формирует байты полезных данных **19, 0**
  (`13 00` hex), не value 48.
- Обработчик ответа выбирает `AvgConsumptionSinceStart` при
  `values[0] == 49`, хотя enum value равен 48. Соответствие реальному
  протоколу без сырого ответа не проверено.

Кроме того, этот обработчик вычисляет результат так:

```java
float result = ((values[1] + values[2]) << 8) / 10;
```

Это не предположение из странного вывода JADX. В `classes.dex` проверены
инструкции `add-int/2addr`, `shl-int/lit8 ... 8`, `div-int/lit8 ... 10`,
затем `int-to-float` (участок около `0x0d5e1a`–`0x0d5e30`).
Для неотрицательных байтов результат будет 0, 25, 51 и т. д., с потерей
дробной части; непосредственно получить обычные 4–5 л/100 км он не может.
Правильную формулу из этого установить нельзя.

Проверенный APK: CanBusService 1.2.0 (7), SHA-256
`96ac5182e795ad70c43c78f26b9cf29e76b59db67c2d5c09216ba1d8425c427c`.

Следующий эксперимент, когда снова будет доступна машина: после проверки
совместимости запроса с её MCU выполнить один такой запрос и сохранить
исходный ответ 45, если он придёт. Callback без сырого ответа недостаточен
для вывода о правильности расхода. Автоматический опрос и внедрение этого
API в виджет на текущем этапе не обоснованы.

## Сообщение 142: определена контрольная сумма

Нерасшифрованный Netlink 142 соответствует MCU `0x16E5`. Для его
восьмибайтового payload установлена проверяемая зависимость:

```python
def payload_checksum(data):
    crc = 0
    for byte in data[:7][::-1]:  # b6, b5, ..., b0
        crc ^= byte
        for _ in range(8):
            crc = ((crc << 1) ^ (0x1d if crc & 0x80 else 0)) & 0xff
    return crc                  # совпадает с b7
```

Совпали **846 из 846 MCU-записей** и **1141 из 1141 сообщений Netlink 142**
в трёх окнах. Старшая половина b6 перебирает 0–15; последовательность
согласуется со счётчиком кадров с пропусками в журнале. Таким образом,
b7 можно исключить из поиска расхода, а верхние четыре бита b6 учитывать
как кандидат служебного счётчика, не накопленного топлива.

Та же контрольная сумма подходит нескольким другим MCU-командам и многим
ID старого физического архива. Она **не кодирует уникальный CAN ID**:
по ней нельзя назначить номер 142 конкретному ECU. Остальные поля 142
ещё не расшифрованы. Совпадение номера с `PDCM_IVI` другой модели также
не доказывает расход: тот обработчик описывает режимы и запас хода.

## Накопленный объём топлива и старый физический архив

Проверены монотонные поля как возможные накопители, включая:

- 16/24/32-битные значения с границ байтов;
- 12/16/20/24/32-битные поля со всех битовых смещений, оба порядка байтов;
- для предварительного поиска в физическом архиве — первый кадр каждого
  ID за секунду; найденные основные счётчики затем проверены на всех кадрах.

Отбор требовал не менее восьми различных значений и роста без откатов;
поэтому счётчики с переполнением, сбросом, редким изменением, иной шириной,
мультиплексированием или другой упаковкой могли не пройти фильтр.
Это не доказательство отсутствия счётчика топлива на шине.

У найденных сильных кандидатов обнаружились другие объяснения:

| Источник | Поле | Наблюдение |
| --- | --- | --- |
| MCU `0x12C9` / Netlink 125 / OEM `0x2FE` | u24le b0–b2 | 153812→153822. Прирост 10 совпадает с изменением raw дистанции поездки 351→361 из `FUEL_info`; это кандидат одометра с шагом 0,1 км |
| Архив `0x492` | u16le b0–b1 | 19403→19768, прирост 365 |
| Архив `0x58E` | u16le b2–b3 | 49328→49693, тот же прирост 365 |
| Архив `0x3F3` | u16le b6–b7 | 1017→1382, тот же прирост 365; согласуется с копиями пробега из предыдущего исследования |
| Архив `0x3F3` | b2 | 81→104, шаг раз в 59,924–59,929 секунды: кандидат минутного счётчика |

Достоверного накопленного объёма топлива среди них не выделено. Расчёт
среднего как `100 × Δлитры / Δкм` станет возможен только после нахождения
именно объёма топлива с подтверждённой шкалой и границами периода.
Уровень бака, запас хода и электрический расход его не заменяют.

В физическом архиве есть 13 805 кадров `0x3A1`, однако применение нынешней
H97X-формулы графика ко всем им даёт неизменные индекс 0, бензин 0 и
электричество −20. Это **не подтверждённые измерения расхода**: перенос
раскладки нынешнего OEM-декодера на этот архив не валидирован.
Кадров `0x4CB`–`0x4CF`, которым другие OEM-ветки назначают распределение
расхода и дневные средние, в архиве нет.

## Результат и ограничения

Офлайн-проверка сузила поиск: исключены хвост `FUEL_info`, несколько
числовых совпадений и служебные байты 142; найден отдельный запрос
статистики и проверена проблема его декодера. Число 4–5 не было записано
с точным синхронным временем, поэтому подобрать под него произвольную
шкалу неизвестного поля нельзя.

Следующие реальные опоры — сырой ответ на проверенный запрос статистики,
таблица пересылки MCU, код декодера QNX либо синхронная запись физической
шины нынешней H97X с несколькими контрольными показаниями приборки.
Существующий архив от 26.06.2025 не установлен как запись этой машины.

Выполнены повторный разбор payload, поиск и проверка счётчиков,
проверка контрольной суммы на двух транспортных уровнях, сверка DEX,
локальных ссылок и `git diff --check`. Изменена документация;
сборка APK и **пересборка установщика не нужны**. Чтение автомобиля,
отправка запросов, установка и публикация не выполнялись.
