# Приёмка OTA на головном устройстве

Проверяется единый payload с runtime из `Packaging/new/` и Installer 1.8.1 или
новее, совместимым с его требованиями. Версию и модель автомобиля фиксируют
перед прогоном. [Прежние локальные результаты](ota-local-validation.md) относятся
к старым сборкам: они не подтверждают текущий релиз, OEM init/SELinux и питание ГУ.

## Подготовка

Соберите согласованный релиз по [инструкции выпуска](releasing.md), задав минимум
OTA по совместимости службы. Для первого внедрения новой службы используйте USB.
Ранее опубликованный ZIP не получает новый код от изменения записи каталога.

Архив и выбранный HTTPS-каталог должны быть доступны с ГУ. По умолчанию используется
`https://voyahtune.ru/api/v1/releases`; для изолированной приёмки можно задать
другой HTTPS-источник того же [формата](ota-release-format.md).
Локальные индексы в репозитории не ведутся. Подготовка и публикация тестового
источника выполняются отдельно в согласованном объёме.

Зафиксируйте версию, размер и SHA-256 ZIP, `minimumInstallerVersion` и
`minimumOtaVersion`. Для повторов используйте те же байты архива. Локальная
проверка payload не подтверждает доступность сетевого источника.

## Шесть этапов

1. **Проверка артефактов.** Проверьте manifest и recipe через `verify-payload`,
   параметры записи — через `verify-ota`. Выберите нужный релиз в актуальном GUI
   либо импортируйте локальный ZIP. Новый GUI собирайте только при изменении
   его поведения, ресурсов или поддерживаемого контракта.
2. **Первая установка через USB.** Установите единый релиз поверх прежнего.
   Сохраните отчёт. Запишите несколько пользовательских настроек для сравнения
   после OTA. Должны примениться очистка старого runtime и условие RunYN по модели;
   Installer должен подтвердить службу и новый загрузчик после перезагрузки.
3. **Служба и экран.** Откройте «Другое → Обновления VoyahTune».
   Проверьте установленную версию, состояние службы и каталог. Экран работает
   внутри RestoreMode в процессе `:ota`; служба запускается init независимо от APK.
   Закрытие и повторное открытие экрана не должны отменять активную операцию.
4. **Скачивание и установка.** Выберите тестовый релиз, скачайте его и дождитесь
   проверки. Проверьте повторную установку текущей версии. На стоящем автомобиле
   в P при стабильном питании подтвердите установку и reboot. Проверка каталога
   и уведомление сами по себе не должны скачивать архив или запускать запись.
5. **Журналы.** Сохраните локальную диагностику через USB. В сессии должны быть
   загрузка, проверка, установка файлов/APK, `reboot-pending`, новая загрузка и
   проверка hooks. Итог — `committed` либо подробная причина ошибки. Кнопок
   просмотра/выгрузки журнала OTA в пользовательском UI нет.
6. **Функции автомобиля.** Проверьте Native/RestoreMode, RunYN на применимых
   моделях, оба экрана, настройки и DNS, холодный старт и сон/пробуждение.
   Проверьте суточный интервал автопроверки после перезапуска. Для уведомления
   используйте более новую версию: переустановка текущей его не создаёт.

После reboot служба проверяет Android, Native DE, применимый RunYN и
`voyahtune-loader --check-hooks`. Ошибка hooks не подтверждает установку.
Это не полная проверка автомобильных функций и не обещание 30-секундного
наблюдения всех приложений: [точный рабочий цикл](ota-updater.md#рабочий-цикл).
Результаты этапа 6 фиксируются отдельно от автоматического завершения.

## Ошибка и USB-восстановление

При ошибке или прерывании записи автоматического продолжения и отката нет.
Экран показывает причину и предлагает USB-восстановление. Если Android или служба
не работают, диагностика выполняется через root ADB. Логи сохраняйте до следующей
OTA-сессии: её начало очищает прежние сессионные журналы.

Независимая выгрузка без запуска приложений:

```sh
python3 Installer/scripts/ota-usb-diagnostics.py \
  --adb /path/to/adb --serial DEVICE_SERIAL --output /path/to/new-diagnostics-directory
```

Повторите установку совместимым GUI. Он сохраняет OTA journal и логи в
`ota-diagnostics` отчёта до очистки состояния. Настройки адреса каталога сохраняются;
блокировка после прерванной OTA снимается после записи релиза.

Если оборвался компьютерный установщик, сначала закройте все его экземпляры.
Затем повторите выгрузку в новый каталог с `--release-stale-desktop-lock`.
Этот ремонт снимает только блокировку desktop; активный OTA lock не удаляется.
После диагностики повторите установку через GUI.
