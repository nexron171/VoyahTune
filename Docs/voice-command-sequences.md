# Последовательности голосовых команд

Одна голосовая фраза может содержать до трёх команд, разделённых словами «и», «далее», «затем»,
«потом». Сегменты выполняются по порядку произнесения, и отклоняется только тот сегмент, который
нельзя исполнить однозначно: остальные команды выполняются, а отклонённый сегмент показывается
на экране распознавания красной строкой с причиной.

Примеры:

| Фраза | Результат |
| --- | --- |
| «включи режим топливо затем режим комфорт потом включи массаж» | три принятых сегмента: `energy:SREV`, `drive:COMFORT`, `seat:driver:massage:on` |
| «включи режим топливо затем открой окно потом включи массаж» | третий сегмент не достигнут: второй отклонён, «открой окно» — красная строка «Не указано, какое окно» |
| «перезагрузи систему и включи массаж» | «Требует подтверждения» + массаж выполнен |
| «открой демо затем включи массаж» | «Недоступна в последовательности» + массаж выполнен |
| «включи массаж затем включи подогрев руля затем включи фары затем выключи фары» | первые три выполнены, четвёртый отклонён: «Больше 3 команд в одной фразе» |

Одиночная фраза сохраняет прежнее поведение без изменений: диалог подтверждения для перезагрузки,
закрытия сторонних приложений и своей CAN-команды, прежние сообщения об ошибке и прежние тайминги.
До этой доработки несколько разных команд в одной фразе отклонялись целиком.

## Разбор фразы

Порядок обязателен и выполняется классом `VoiceCommandSequence`:

1. Сначала проверяется **полное совпадение всей фразы** через `VoiceCommandCatalog.match`. Это
   защищает опубликованные фразы, в которых «и» является частью названия: «включи форс и ви»
   остаётся одной командой `forced_ev:on`.
2. Затем фраза делится по жёстким разделителям «далее», «затем», «потом» — они всегда считаются
   разделителями и не несут смысла команды.
3. Внутри каждого фрагмента «и» делит текст только там, где хотя бы одна из частей уже распознаётся
   как команда. Поэтому «включи форс и ви затем подогрев руля» даёт две команды, а «включи форс»
   без продолжения не превращается в команду.
4. Каждый сегмент разбирается точным сопоставлением и ограниченным исправлением словаря
   (`VoiceCommandRepair`). Нечёткий поиск по расстоянию Левенштейна (`VoiceFuzzyMatcher`) на
   сегментах **не** применяется: на коротких фрагментах он даёт ложные совпадения.
5. Если после деления остался один сегмент, вызывающий код работает по прежнему пути одиночной
   команды.

`VoiceCommandCatalog.REJECT` не менялся: «затем» и «потом» по-прежнему запрещены внутри одиночной
фразы, а в последовательности обрабатываются как разделители до вызова сопоставления.

## Отклонённые сегменты

Сегмент не отправляется в Native, если его нельзя исполнить однозначно. Пользователь видит номер
сегмента, распознанный текст и причину:

| Сегмент | Причина на экране |
| --- | --- |
| перезагрузка, закрытие сторонних приложений, своя CAN-команда (`Command.confirm`) | «Требует подтверждения» |
| окно, люк или шторка без однозначного места («открой окно») | «Не указано, какое окно» |
| сиденье без однозначного места, два места или уровня | «Не указано место» |
| отрицание: «не», «ни», «нет», «нельзя» | «Отрицание в команде» |
| противоречивые глаголы («включи … выключи …»), «или», «если», отмена | «Неоднозначная команда» |
| слова, не образующие команду | «Не распознана» |
| приложение, сплит, звонок, «назад», открытие VoyahTune не последним сегментом | «Недоступна в последовательности» |
| четвёртый и последующие сегменты | «Больше 3 команд в одной фразе» |

Причины «Не указано, какое окно» и «Не указано место» — понятные пользователю подсказки, а не
детальный диагноз парсера: они выбираются по упоминанию окна, люка, шторки, сиденья или места.

## Выполнение и экран

- Сегменты отправляются по одному, следующий — только после ответа Native на предыдущий. Порядок
  произнесения становится порядком исполнения, очередь CAN сохраняется общей `ApplyEngine`.
- Отказ одного сегмента или ошибка его выполнения не останавливают последовательность: строка
  получает красную пометку, остальные команды продолжают выполняться.
- Строки результата строятся в `VoiceActivity` под расшифровкой: принятые — белым, отклонённые —
  красным `0xffff6b6b` с причиной `0xffffb0b0`. Состояния: «Отправляю…», «Выполнено», «Команда
  отправлена» (сиденья, подогрев руля, окна), подтверждение уровня заряда, оценка заправки.
- Статус в центре экрана: «Передаю команды…», «Команда N из M…», затем «Команды переданы».
- Экран удерживается `max(3 с, 1,2 с × число выполненных)`; для подтверждённого лючка бензобака
  действует прежнее правило 10 секунд.
- На одну команду отводится 8 секунд (`COMMAND_TIMEOUT_MS`), на всю последовательность — 20 секунд
  (`SEQUENCE_BUDGET_MS`). Превышение бюджета закрывает экран сообщением «Выполнение команд занимает
  слишком много времени».
- Если отклонены все сегменты — «Команды не распознаны»; если ни одна команда не выполнилась —
  «Команды не выполнены». В обоих случаях список строк остаётся на экране, звучит сигнал ошибки.
- Звук успеха звучит, если выполнена хотя бы одна команда.
- Уход с экрана после отправки первой команды не отменяет уже отправленное действие, как и в
  одиночном режиме; отправленная в автомобиль команда не откатывается.
- Отладочный предпросмотр (`previewState`) получил состояние `sequence` со образцом
  `VoiceCommandSequence.sample()`.

## Протокол RestoreMode — Native

- Op остаётся `execute`; в bundle добавлены `index` и `count` (`VoiceCommandMessage.create`).
  Прежний вызов без этих полей даёт `count = 1`, то есть старое поведение.
- `VoiceSessionGate` вместо boolean-флага хранит номер следующего сегмента: `submit(token, index)`
  принимает сегменты строго по порядку, повтор и пропуск номера отклоняются. Новая сессия сбрасывает
  счётчик, поэтому поздние ответы прежней сессии не продвигают последовательность.
- `VoiceCommandController` читает `index`/`count`, проверяет их диапазон и дополнительно отклоняет
  навигацию не последним сегментом («Навигация только последней командой»), не доверяя UI.
- Ветки исполнения Native не дублировались: сегменты проходят те же обработчики, что и одиночные
  команды (сиденья и окна, `port_cap:`, `fuel_charge:`, `drive:`/`energy:`/`recycle:`, `power_hold`,
  службы `apply`/`battery_heat`/`auto_light:`).
- Требуется обновить оба приложения: новый RestoreMode со старым Native выполнит только первый
  сегмент, остальные будут отклонены гейтом.

## Осознанные ограничения

- Не более трёх сегментов: лимит записи распознавания остаётся 10 секундам
  (`VoiceRecognizer`, `frames < 1000`), и три команды с разделителями в него укладываются.
- Межсегментные конфликты не проверяются: «включи эко и спорт» выполнит два переключения подряд,
  как и произнесено. Внутри одного сегмента противоречивые глаголы по-прежнему отклоняются.
- Навигация считается только по позиции в произнесённой фразе. Поэтому «открой музыку затем открой
  окно» отклоняет оба сегмента, хотя второе приложение формально оказалось бы последним из принятых.
- Подтверждаемые команды в последовательности не выполняются, диалог для них доступен только в
  одиночной фразе.
- «Требует подтверждения» относится к подтверждению пользователем. Отдельно остаются проверки
  автомобиля: для лючков и режима мойки нужно положение P, для Power Hold — заряд не ниже 15%,
  прогрев батареи подтверждается штатным виджетом. Это по-прежнему условия выполнения, а не разбора:
  строка принимается, а ошибка появляется в списке по факту.
- Успешная отправка и «Команда отправлена» не означают подтверждённое изменение состояния машины.

## Реализация

- `RestoreMode/app/src/main/java/ru/big/town/restoremode/voice/commands/VoiceCommandSequence.java` — деление фразы,
  классификация сегментов, причины отказа, признак навигации, образец для предпросмотра.
- `voice/ui/VoiceAssistantActivity.java` — `recognized`, `recognizedSequence`, `stepSequence`, `completeStep`,
  `noteFor`, `finishSequence`, `showRows`/`clearRows`, список строк результата и тайминги.
- `VoiceCommandMessage.java` — перегрузка `create` с `index`/`count`.
- `Native/.../VoiceSessionGate.java` — порядковые номера сегментов.
- `Native/.../VoiceCommandController.java` — разбор полей, защита навигации.
- Тесты: `VoiceCommandSequenceTest` (JVM, RestoreMode), `VoiceSessionGateTest` (JVM, Native),
  `VoiceCommandMessageTest` и эхо-сервис `VoiceReplyTestService` (инструментальные).

## Проверки

Локально выполнено и подтверждено:

- `cd RestoreMode && ./gradlew testDebugUnitTest` — успешно.
- `cd Native && ./gradlew testDebugUnitTest` — успешно.
- `cd RestoreMode && ./gradlew assembleDebug`, `cd Native && ./gradlew assembleDebug` — успешно.
- `git diff --check` — без замечаний.

Инструментальные тесты `VoiceCommandMessageTest` и `VoicePipelineNativeTest` не запускались:
устройство не подключено. Аудиофикстура для фразы из нескольких команд не добавлена, поэтому
распознавание последовательности целиком остаётся проверкой на автомобиле: качество записи,
поведение разделителей «и»/«далее»/«затем»/«потом» в реальном салоне и реакция штатных узлов
на два-три действия подряд.

## Влияние на релиз

Изменены общие APK RestoreMode и Native, поэтому нужен новый payload и обновление каталога
(`make_release.sh <версия> --payload`, затем `verify-payload` и `update-catalog.py`).
Пересборка GUI установщика не требуется, пока не менялись встроенный recovery/remover, движок или
контракт payload; `minInstallerVersion` не повышается.
