# Отладочная информация

Переключатель «Режим отладки» в разделе «Другое» показывает блок
«Отладочная информация». Значение сохраняется в настройках RestoreMode; блок
появляется и скрывается сразу после переключения. При открытом блоке показываются
сырые значения семи источников света (последний — при наличии Android-датчика):

| Показатель | Источник | Обновление |
| --- | --- | --- |
| SWReason | `BCM_RSM_lightSWReason` (1072) | CAN-событие, начальное чтение и опрос раз в секунду |
| Внешняя освещённость | `BCM_RSM_AmbBrightness` (1071) | CAN-событие, начальное чтение и опрос раз в секунду |
| Освещённость впереди | `BCM_RSM_FwBrightness` (1070) | CAN-событие, начальное чтение и опрос раз в секунду |
| ИК-освещённость | `BCM_RSM_IRBrightness` (1073) | CAN-событие, начальное чтение и опрос раз в секунду |
| Уровень света | `CarSignalService.getLightSensorLevel` | callback 13 и начальное чтение |
| PAS уровень света | `CarSignalService.getPASLightSensorLevel` | callback 25 и начальное чтение |
| Освещённость Android | `Sensor.TYPE_LIGHT` | `SensorEventListener`, при наличии датчика |

`SWReason` дополнительно расшифровывается: 0 — день, 1 — другое, 2 — темно,
3 — тоннель, 4 — начало темноты. Неизвестные коды показываются числом. Для
остальных OEM-полей единицы измерения и диапазоны не подтверждены, поэтому
показываются только исходные целые значения. Android `TYPE_LIGHT` показывается
в люксах согласно стандартному API. Прочерк означает, что актуальное
значение получить не удалось; это не ноль. При потере соединения показания
соответствующего транспорта сбрасываются.

Переключатель управляет видимостью блока, read-only подписками и опросом OEM-источников,
пока открыт этот раздел настроек. Отправка CAN-команд, управление фарами,
восстановление режимов, управление подвеской и сервисные действия не зависят от
него. Прежний код эмуляции команд удалён.

Колонка 12 `debugMode` в ContentProvider сохранена для совместимости с прежним
форматом ответа, но всегда равна 0. Это позволяет ранее внедрённым хукам не
отменять восстановление режимов при включённом новом интерфейсном переключателе.
Доступность OEM-показателей и Android-датчика на официальных SE и Sport+ 2025–2026 нужно
проверить на автомобиле. CAN-идентификаторы сверены с декомпиляцией
VehicleSettings SportEdition 2025 rc5.1; методы и callback CarSignal — с
локальной декомпиляцией CarSignalService, точная версия APK не установлена.
Наличие поля в этих API не подтверждает, что конкретная машина выдаёт значение.
Показатель подсветки дисплея
`getIllumination` сюда не включён: он отражает режим экрана, а не отдельный
измеренный уровень внешнего света.

## Если значения не меняются

`SWReason` — причина переключения света, а не измерение освещённости: при
изменении яркости код может оставаться прежним. Три строки RSM — отдельные поля.
Native читает все четыре RSM-поля, включая SWReason, через `getVehicleState`
(TX57) при подключении диагностической подписки и далее раз в секунду.
Изменения также приходят через `onVehicleStateChanged` (callback 36) общего
`CanBusEventHub`. Повторное открытие раздела запускает начальное чтение заново.

Опрос выполняется в рабочем потоке через существующий `OemVehicleStateTransport`
только при открытой отладке и подключённом CAN. При закрытии раздела, уходе
приложения в фон или потере соединения таймер останавливается. Если предыдущее
чтение ещё не завершено, очередной секундный запрос пропускается, чтобы не
накапливать работу. Событие, полученное во время чтения, имеет приоритет над
результатом этого чтения для соответствующего поля. Результаты прежнего
подключения отбрасываются; при ошибке чтения поля без более свежего события
показывают прочерк. Протокол Native/RestoreMode не меняется.

В исследованном локальном CanBusService 1.2.0 (versionCode 7), в обработчиках
Dongfeng и DongfengH97C, `getVehicleState` возвращает OEM-кэш. Это не запрос
нового измерения у датчика. Обработчики входящих данных обновляют кэш и
уведомляют подписчиков при изменении значения. Соответствие этого APK прошивке
конкретного автомобиля нужно проверять отдельно.

Поэтому неподвижное число само по себе не доказывает зависание интерфейса.
Если повторное открытие даёт то же число, периодическое чтение того же кэша
не гарантирует исправления. Для локализации нужны [логи](collect-logcat.md)
за время изменения освещения при открытом разделе: начальные строки
`TX57 getVehicleState BCM_RSM_…` Native, сообщения `CanBusEventHub` и OEM
`onVehicleStateChanged` для тех же полей. Следует записать показания всех строк,
модель, прошивку и установленный релиз. Нулевые RSM-поля без подтверждения
живых измерений нельзя трактовать как доказанную нулевую освещённость.
