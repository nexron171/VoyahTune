# Доставка интерфейса Updater после OTA

Механизм реализован для существующих payload schema 4 и recipe `qinggan-v3` schema 3.
Он обновляет только системный APK `ru.big.town.updater`. Root-служба, её init-файл
и bootstrap сохраняются. Предварительная USB-установка новой службы не требуется
для служб, уже поддерживающих этот формат и файловые операции recipe.
Работа на OEM Android 11 требует отдельной приёмки: локальные тесты не подтверждают
сканирование заменённого системного APK и сохранение его регистрации на автомобиле.

## Доставка

[Сборщик payload](../Installer/crates/installer-build/src/main.rs) добавляет два
обычных файловых артефакта:

| Артефакт | Путь на ГУ | Источник |
| --- | --- | --- |
| `voyahtune-ui-maintenance` | `/data/local/bin/voyahtune-ui-maintenance` | ARM64 executable Updater с режимом `--update-ui` |
| `voyahtune-ui-next.apk` | `/data/local/bin/voyahtune-ui-next.apk` | Новый APK интерфейса Updater |

Это отдельные имена, которые прежний OTA-исполнитель копирует как обычные файлы.
Прежние артефакты инфраструктуры по-прежнему входят в список `STABLE` и пропускаются.
Хеши обоих новых файлов включаются в подписанные метаданные Native и RestoreMode.
Файлы находятся вне staging службы и остаются после очистки успешной OTA.

Тело [загрузчика](../Packaging/system/voyahtune.load.sh) запускает процесс обслуживания
в фоне и сразу запускает `load.bin`. Init-контракт `voyahtune.load.rc` не меняется.
Ожидание обслуживания не задерживает hooks, необходимые для проверки основной OTA.
Новый Updater имеет versionCode 3 / versionName 0.3.0. При следующих изменениях APK
нужно повышать versionCode: замена отличающихся байтов с прежним или меньшим кодом запрещена.

## Проверки и замена

[Процесс обслуживания](../Updater/daemon/src/ui_update.rs) работает от root.
Собственный flock исключает второй процесс; общий lock установки исключает USB и OTA apply.
Он ждёт загрузки Android и завершения основной OTA до десяти минут. При занятой
установке, движении или отказе проверок изменение откладывается до следующего запуска загрузчика.

Перед заменой проверяются:

- фаза службы `committed` или `idle`, отсутствие блокирующего файла и прежний fingerprint;
- совпадение установленной версии с подписанными метаданными активных Native и RestoreMode,
  одинаковые build revision, runtime hashes и APK-подписи обоих приложений;
- подписи и хеши нового APK, package ID, больший versionCode и хеш самого процесса обслуживания;
- принадлежность staged-файлов и системного Updater root; активные APK Native/RestoreMode
  могут принадлежать PackageManager (UID 1000); отсутствие симлинков и записи для группы/остальных;
- системный путь активного Updater: APK из `/data/app` не допускается;
- подтверждение через Native связи приложений, P и нулевой скорости перед записью
  и повторно перед дополнительной перезагрузкой.

Служба останавливается только после получения общего lock и повторной проверки её фазы.
Неизвестная/незавершённая операция или `repair-required` не разрешает замену. Если
системный APK уже совпадает с ожидаемым и PackageManager зарегистрировал его versionCode,
запись и дополнительная перезагрузка не выполняются. Начальная замена требует сохранённого
подтверждения успешной OTA (`installedArchiveSha256`); чистая USB-установка уже содержит
тот же APK и не нуждается в замене.

Старый APK копируется в `VoyahTuneUpdater.apk.ui-backup` в том же системном каталоге.
Имя копии не заканчивается на `.apk`. В приватном каталоге службы сохраняется
`ui-update.json`: хеши старого/нового APK, прежний versionCode, boot ID и состояние отката.
Журнал и копия сохраняются до атомарной замены системного APK с правами 0644,
владельцем root и `restorecon`. Данные приложения не удаляются, `pm install -r` не используется.
Затем выполняется дополнительная перезагрузка.

После неё проверяются системный путь, SHA-256 APK и versionCode из PackageManager.
При успехе копия и журнал удаляются. Если PackageManager не зарегистрировал новую версию,
восстанавливается проверенная копия старого APK и выполняется одна перезагрузка для отката.
Подтверждённый откат сохраняется в журнале и не запускает бесконечные повторы.
Повторный запуск после прерывания до rename может продолжить замену на новой загрузке;
если запись отката прервана, проверенная копия может быть восстановлена повторно.
Изменённый сторонним установщиком APK и журнал другой целевой версии не перезаписываются.

Записи `ui_update_install_reboot`, `ui_update_complete`, `ui_update_rollback_reboot`
и `ui_update_error` находятся в `/data/local/voyahtune-updater/updater.log`.
В логах нужно различать успешную основную OTA и отдельный результат замены интерфейса.
Ошибка последнего этапа не превращает уже завершённую OTA в `repair-required`.

## Совместимость интерфейса

RestoreMode открывает Updater в новой очищенной задаче с флагом начального экрана.
Если служба поддерживает `finish`, завершённый результат сбрасывается в её журнале.
Прежняя служба возвращает точную ошибку неизвестной команды: интерфейс скрывает
только представление `committed`, сохраняя факты службы. Кнопка проверки использует
прежнюю команду `check`. Активные операции, скачанный релиз и ошибки восстановления
сохраняются. Запуск из launcher сохраняет обычный экран результата.

## Выпуск и проверки

Для OTA нужен новый полный payload с пересобранными Native и RestoreMode:
их подписанные метаданные должны содержать новые recipe и хеши. Сборщик сам строит
ARM64 executable и APK интерфейса до подписания этих метаданных.
Версия/минимум Installer и capabilities не повышаются: новый контракт GUI не нужен.
Существующий GUI умеет устанавливать этот payload и удалять его по сохранённому recipe.
Для обновления встроенного аварийного remover нужна пересборка GUI согласованных
платформ: его встроенный recipe теперь включает два новых файла. Это не является
условием OTA-доставки на уже установленную систему.

Локальные проверки: Rust-тесты Updater и Installer, JVM-тесты Updater,
ARM64/release-сборки и проверка полного payload. Тест
[`test_updater_ui_worker.py`](../Packaging/tests/test_updater_ui_worker.py) выполняет
секцию запуска загрузчика с ожидающим процессом обслуживания и подтверждает,
что hooks запускаются до завершения обслуживания.

Приёмка на ГУ должна отдельно подтвердить обновление с прежней службой, дополнительную
перезагрузку, активный системный APK, сохранение UID/данных, обе формы «Завершить»,
работу без записи при одинаковом APK и восстановление после прерывания.
Публикация и установка не считаются выполненными по локальным сборкам.
