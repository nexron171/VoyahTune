# Механизм обновления VoyahTune

Один единый payload используется компьютерным установщиком и root-службой OTA.
Он содержит Native, RestoreMode со встроенным экраном обновлений, RunYN по условию
модели и runtime из `Packaging/new/`. Текущий контракт — payload schema 4,
recipe schema 3 / `qinggan-v3`, Installer 1.8.1 и `unified-runtime-v1`.
[Полный состав](installer-payload.md) · [Протокол](installer-protocol.md).

## Доставка и проверка

Installer и OTA по умолчанию читают серверный каталог
`https://voyahtune.ru/api/v1/releases`. Поле `url` задаёт адрес архива, остальные
поля — версию, размер, SHA-256 и минимумы совместимости.
Локальные JSON-индексы больше не ведутся. [Формат каталога](ota-release-format.md).

Общие модели и проверки находятся в `release-core`: ZIP проверяется по размеру
и SHA-256, payload — по manifest, recipe, хешам файлов и подписанным metadata APK.
HTTPS-каталог является доверенным источником контрольной суммы; отдельной подписи
записи OTA нет. Пользовательский HTTPS-источник сохраняется в настройках.

`minimumInstallerVersion` относится к компьютерному установщику,
`minimumOtaVersion` — к установленному VoyahTune с совместимой root-службой.
Первый переход на новую несовместимую службу выполняется через USB. Следующие
совместимые релизы используют OTA без замены бинарника службы, её init и bootstrap.

## Исполнители

[USB-движок](../Installer/crates/installer-core/src/engine.rs) работает на компьютере
через ADB: root/remount, подготовка, файловый recipe, установка APK, DNS,
перезагрузка и проверка запуска. Общий recipe заменяет runtime и очищает известные
старые компоненты. [Процесс установки](installer-classic-port.md).

OTA выполняет независимый root-процесс `voyahtune-updater`. Native остаётся
привилегированным Android-приложением, а экран OTA работает в отдельном APK
`ru.big.town.updater`. Закрытие экрана или замена RestoreMode не прерывают исполнителя. Сеть,
журнал и применение находятся в службе; UI управляет ею через закрытый init-сокет.
Внешние Intent не принимают архивы, URL или команды установки.

USB и OTA не используют файловый lock установки; старые lock-файлы игнорируются.
Службу запускает Android
init; доступ к сокету проверяется по UID и подписи Updater/RestoreMode. OEM init/SELinux,
питание и конкретные функции автомобиля требуют отдельной проверки на ГУ.
Суточная проверка каталога не начинает скачивание или установку.

## Завершение и восстановление

Общий исполнитель устанавливает RestoreMode последним APK, затем фиксирует
`reboot-pending` и перезагружает Android. Это освобождает прежний код в целевых процессах.
После загрузки комплект runtime проверяется однократно через `voyahtune-loader --check`.
Лёгкий `--check-hooks` проверяет актуальность загрузчика и подтверждённые состояния
обязательных модулей, возвращая идентификаторы процессов. Исполнитель наблюдает их
10 секунд; динамические клиенты не задерживают завершение. Точные проверки и ограничения
перед записью и после reboot — в [описании root-службы](ota-updater.md#рабочий-цикл).

Компьютерный установщик сохраняет системные/runtime-резервные копии и журналы
на компьютере. Native и RestoreMode APK не резервируются. При несовпадающей
подписи соответствующее приложение может быть переустановлено со сбросом данных.

OTA сохраняет журнал на ГУ, но не создаёт резервную копию всего релиза и не
выполняет автоматический откат. Прерывание записи требует диагностики и повторной
установки через USB. Атомарная замена одного файла не делает атомарным весь релиз.
[Приёмка и USB-диагностика](ota-acceptance.md).

Новый совместимый payload не требует нового GUI. Пересборка Installer нужна,
если меняются его исполняемое поведение, встроенные ресурсы или поддерживаемые
операции/capabilities. Изменение root-службы доставляется через USB в payload;
необходимость нового GUI оценивается отдельно. [Подготовка выпуска](releasing.md).
