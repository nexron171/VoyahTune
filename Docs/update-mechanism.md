# Механизм обновления VoyahTune: текущие ограничения

Состояние рабочего дерева на 2026-09-27 после унификации формата релиза;
исходная точка исследования — commit `1e0c9e2`, версия APK 3.14.0.
Это описание существующей реализации и границ её повторного использования.
OTA-клиент и автономный установщик на ГУ пока не реализованы.
Релиз VoyahTune содержит Native, RestoreMode и системные компоненты.
Выбора редакции и специальных миграций нет.
Первый релиз с поддержкой OTA устанавливается через установщик; следующие
совместимые релизы обновляются из приложения.

## Доставка и состав

[Payload](installer-payload.md) schema 4 содержит одну пару APK,
файловый recipe, права и накопительный список устаревших файлов.
Native устанавливается в `/system/priv-app/Native/Native.apk`, whitelist —
в `/system/etc/permissions/`, RestoreMode — через PackageManager. Релиз также
использует `/data/local/bin/` и boot-файлы в `/system/etc/`.
Источником состава служит [payload-spec.json](../Packaging/installer/payload-spec.json).

[Каталог](../Installer/releases/index.json) содержит URL, размер и SHA-256 ZIP;
локальная запись 3.14.0 указывает архив 143 048 623 байта в Yandex Object Storage.
Сам URL каталога в [catalog.rs](../Installer/crates/installer-core/src/catalog.rs)
пока указывает на GitHub raw. Доступность этих адресов с ГУ здесь не проверялась.
Формат каталога запрещает неизвестные поля: добавление OTA-полей в существующий
index без изменения читателя нарушит совместимость старого GUI.

[Проверка payload](../Installer/crates/installer-core/src/payload.rs) включает
хеши файлов, APK v2 signatures/content digest, metadata APK, recipe digest и
runtime hashes. SHA-256 из HTTPS-каталога сам по себе не подтверждает издателя.
Для автономного root-обновления нужен закреплённый доверенный ключ и проверка
происхождения всего применяемого релиза до изменения файлов.

## Кто выполняет установку

[Движок](../Installer/crates/installer-core/src/engine.rs) работает на компьютере:
`adb root`, remount/при необходимости reboot, backup, остановка runtime, файлы,
boot-hook, Native/whitelist, RestoreMode, DNS, reboot и postflight.
Подробности — в [описании процесса](installer-classic-port.md).

Native является priv-app, но это не UID 0. В его manifest и whitelist нет
`INSTALL_PACKAGES`; выдача AppOps для установки сторонним приложениям не является
root-доступом. В исследованных исходниках Native нет самостоятельного механизма
root/remount/установки payload. RestoreMode в основном manifest также не запрашивает
`INTERNET`. По принятому плану каталог и архив загружает сама root-служба; RestoreMode
только открывает её отдельный экран через Intent. Переносить сетевую загрузку релизов
в RestoreMode не требуется. Собственный интерфейс updater управляет службой по закрытому
внутреннему каналу; внешние команды обновления, архивы и URL не принимаются.
Также запланированы автозапуск службы с системой и VoyahTune и автоматическая проверка
каталога с интервалом не менее 24 часов, сохраняемым между перезапусками. При новой версии
показывается закрываемый информационный экран; его показ и закрытие не скачивают архив
и не запускают установку. Этот механизм пока не реализован.

[Boot-hook](../Packaging/system/voyahtune.load.rc) запускает `voyahtune_load`
от root с `seclabel u:r:su:s0`, предварительно выполняя `setenforce 0`.
[Обёртка](../Packaging/system/voyahtune.load.sh) и loader больше не проверяют режим
установки. Это полезная исходная точка для OTA, но updater должен быть самостоятельной
службой: при замене hooks загрузчик останавливается. Наличие su-domain в rc не
доказывает доступность команды `su` из APK.

SELinux ограничивает также root-процессы; отдельная служба и её IPC требуют проверки
на OEM-политике. [Описание модели SELinux в AOSP](https://source.android.com/docs/security/features/selinux).

## Восстановление и данные

Текущий движок сохраняет backup и журналы на компьютере. Есть локальные транзакции
boot-hook и legacy init.logcat, но нет полного отката всех файлов, APK и данных релиза.
`native_ready()` после reboot проверяет CE/DE, при необходимости выполняет
`install-existing`, отправляет boot broadcast и проверяет процесс Native.
Это не проверка согласованности всего установленного релиза.

При смене APK-подписи GUI может удалить приложение с данными; этот сценарий нельзя
автоматически переносить в OTA с обещанием сохранения настроек. Отдельного mutex
установки на ГУ сейчас нет: блокировка GUI защищает только собственную операцию.

По принятому плану OTA использует исполнитель вне обновляемых APK и постоянный журнал
на ГУ. После штатной перезагрузки служба проверяет работу компонентов. Резервные копии
и автоматический откат не предусмотрены: при ошибке или прерывании установки сохраняются
диагностика и логи, пользователю предлагается установить релиз через USB с компьютера.
Атомарная замена одного файла не делает атомарным весь релиз. Multi-package
PackageInstaller доступен с API 29 для группы APK, однако системные файлы и hooks
не входят в такую группу. [Контракт Android API](https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setMultiPackage()).

Переход к единому контракту требует пересборки APK, GUI и встроенного remover.
Версия Installer — 1.1.0; новый payload требует эту версию и новые capabilities.
Сам OTA ещё не реализован.
